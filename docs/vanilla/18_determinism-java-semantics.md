# 18. 決定性と Java の意味論 (反復順・乱数・整数と浮動小数・連鎖上限)

Java 版 26.3 のレッドストーンの結果は、ブロックのロジックだけでは決まらない。
「ハッシュ表をどの順に回すか」「乱数をいつ何個引くか」「整数がどこで切り捨てられるか」という、
言語とライブラリの性質が結果に混ざる。本メモはそれを 1 か所に集める。

確かさの表記は他のメモと同じである。本メモだけ次の 1 つを足す。

- [ライブラリ実測] JDK 11 の java.util.HashMap と fastutil 8.5.18 を手元で動かし、本メモの規則どおりに書いた写しと反復順を突き合わせた (§4.4)。ゲームを動かした結果ではない

## 2. 全体像

### 2.1 結果を左右する 4 つの要素

| 要素 | 何が決めるか | 再現できるか |
|---|---|---|
| 反復順 | 集合型の実装 (Java 標準・fastutil) と、入れた順・消した順・座標 | できる。型ごとに規則を写す (§4.1〜§4.4) |
| 乱数 | 乱数源の種と、引いた回数 | 実機の列は再現できない。エンジン内では種を渡して決定的にする (§4.6) |
| 数値 | 32 ビット整数のあふれ・切り捨て・単精度の丸め | できる。Rust の型を合わせる (§4.8) |
| 上限と読み込み状態 | 連鎖上限 1,000,000・チャンクのレベル | できる。上限は数えるだけ。読み込み状態は前提を固定する (§4.9・§4.11) |

### 2.2 反復順の決まり方の分類

26.3 のコードに出る集合型は、順の決まり方で 5 種に分かれる。

| 種類 | 型の例 | 反復順 |
|---|---|---|
| 配列・リスト | ArrayList・ArrayDeque・配列の定数 | 入れた順 (定数は書かれた順) |
| 連結つきハッシュ | fastutil の ObjectLinkedOpenHashSet・Int2ObjectLinkedOpenHashMap・Object2IntLinkedOpenHashMap・Long2ObjectLinkedOpenHashMap、Java の LinkedHashMap | 最初に入れた順。入れ直しても位置は変わらない |
| 整列 | PriorityQueue (取り出しのみ)・LongAVLTreeSet・EnumMap | 比較の順・キーの昇順・列挙の宣言順 |
| Java のハッシュ | java.util.HashSet・HashMap | 入れ物の番号の昇順。同じ入れ物の中は入れた順 (§4.2) |
| fastutil の開番地ハッシュ | Object2ObjectOpenHashMap・Long2ByteOpenHashMap・Long2LongOpenHashMap・LongOpenHashSet・ObjectOpenHashSet | 0 キーが先頭。続いて配列の添字の**降順** (§4.3) |

下の 2 種だけが「座標や履歴で順が変わる」。上の 3 種は入力の順さえ守れば自然に合う。

## 4. 処理の詳細

### 4.1 入れた順で決まる型

| 型 | 入れる | 消す | 反復 |
|---|---|---|---|
| ArrayList | 末尾に足す | 詰める | 先頭から |
| ArrayDeque | 用途による (push は先頭・add は末尾) | 先頭から取る | 先頭から |
| fastutil の連結つき (Linked がつく型) | 新しいキーは末尾につなぐ。**既にあるキーは位置を変えない** (値だけ置き換わる) | 連結から外す | 最初に入れた順 |
| PriorityQueue | 二分ヒープ | 最小を取る | 取り出しは比較の順。同点の順は保証されない |
| LongAVLTreeSet | 平衡木 | 平衡木 | キーの符号つき昇順 |
| EnumMap | 列挙の番号の配列 | — | 宣言順 |

連結つきの型は、内部の配置 (どの添字に入るか) は開番地で決まるが、反復は連結をたどる。
内部の配置は反復順に出ない。Rust では「挿入順を保つ集合」で足りる。

ObjectLinkedOpenHashSet の「同じ内容は 2 度入らない」は equals で決まる。
ブロックイベントの同一性は → 03。

### 4.2 java.util.HashSet と HashMap の反復順 (ライブラリの仕様)

HashSet は中身が HashMap である (要素をキーにする)。以下は両方に当てはまる。

**入れ物の番号の決め方**

1. キーのハッシュ値 h (32 ビット) を取る。
2. 撹拌する: 「h と、h を符号なしで 16 ビット右へずらした値との排他的論理和」。これを s と書く。
3. 入れ物の数 n (2 の累乗) に対し、番号は s の下位ビット (s と n − 1 の論理積)。

**入れる (新しいキー)**

1. 表が未作成なら、入れ物 16 個・しきい 12 で作る。
2. 番号の入れ物が空なら、そこに置く。
3. 空でなければ、入れ物の中のつながりを先頭からたどる。同じキーがあれば**値だけ置き換える** (位置は変えない)。
4. 無ければ**末尾に**つなぐ。
5. 末尾につないだ結果、その入れ物が 9 個以上になったら「木構造化」を試みる。
   - 入れ物の数が 64 未満なら、木にせず**表を 2 倍に拡張する**。
   - 64 以上なら、その入れ物を赤黒木にする。
6. 要素数を 1 増やす。しきいを超えたら (13 個目・25 個目・49 個目…) 表を 2 倍に拡張する。

**拡張**

1. 入れ物の数を 2 倍にする。しきいも 2 倍にする。
2. 古い入れ物 j の中身を、つながりの順を保ったまま 2 本に分ける。
   撹拌後の値 s の「古い入れ物数のビット」が 0 のものは新しい入れ物 j に、1 のものは j + 古い入れ物数に入る。
3. どちらの列も、元の相対順を保つ。

**消す**

つながりから外すだけである。表は縮まない。残った要素の相対順は変わらない。

**反復**

入れ物を番号 0 から昇順に見る。1 つの入れ物の中はつながりの順 (= その入れ物に入った順)。
keySet・entrySet・values はすべて同じ順である。

**初期の大きさを指定して作る場合**

集まりを渡して HashSet を作ると、入れ物の数は「要素数 ÷ 0.75 + 1 と 16 の大きい方」を 2 の累乗へ切り上げた値になる。
そのあと渡した集まりの反復順に 1 個ずつ入れる。guava の Sets.newHashSet に集まりを渡した場合も同じである。R8 が該当する。

**木構造になった入れ物**

- 木にした直後は、つながりの順を保つ。ただし木の根が入れ物の先頭へ移される。
- その後に入った要素は、つながりの上では「木の上の親の直後」に入る。
- 木の上の位置は撹拌後のハッシュ値の大小で決まる。値が同じで比較もできないキーどうしは、クラス名と**識別ハッシュ**で決める。
- BlockPos は Vec3i の比較を継承しているが、HashMap が比較に使うのは「自分のクラスと直接比べられる」と宣言したクラスだけである。BlockPos はこれに当たらない。よって完全に同じハッシュ値の BlockPos どうしは識別ハッシュで並び、**起動ごとに変わりうる**。

木構造が起きる条件は「入れ物数 64 以上の表で、1 つの入れ物に 9 個」である。
R1 (7 個) と R2 (最大 12 個) は表が 64 に届かないので、木構造には**ならない**。
R8・R15 は要素が多いので理屈の上では起こりうる。[要実機: 実際に 9 個が同じ入れ物に入る配置があるか]

**BlockPos をキーにしたときの番号の早見**

h の下位 4 ビットは「x − y + z」を 16 で割った余りと同じである (31 は 16 を法として −1、961 は 1)。

| h の範囲 | 入れ物 16 個のときの番号 |
|---|---|
| 0 〜 65535 | (x − y + z) を 16 で割った余り |
| −65536 〜 −1 | 15 − ((x − y + z) を 16 で割った余り)。順が**逆向き**になる |
| それ以外 | h の 16〜19 ビット目との排他的論理和。式どおりに計算する |

h は「961 × z + 31 × y + x」なので、z が 68 前後を超えるか、z が −69 前後を下回ると上の 2 行から外れる。
座標が違えば順が変わる、という事実だけを覚え、実装は式どおりに計算する。

**R1 の実例** [ライブラリ実測]

ダストの 7 要素 (自分・下・上・北・南・西・東の順に入れる) を、実際の Java の HashSet に入れて反復した結果である。

| 自分の座標 (x, y, z) | 反復順 |
|---|---|
| (−2, −60, −3) | 下 → 南 → 東 → 自分 → 上 → 北 → 西 |
| (1000, 64, −2000) | 上 → 北 → 西 → 自分 → 下 → 南 → 東 |

2 つの順はちょうど逆である。同じ回路でも置く場所で配る順が変わる。

### 4.3 fastutil の開番地ハッシュの反復順 (ライブラリの仕様)

連結つきでない型 (Object2ObjectOpenHashMap・Long2ByteOpenHashMap・Long2LongOpenHashMap・LongOpenHashSet・ObjectOpenHashSet ほか) の規則である。
fastutil は Apache License 2.0 で公開されている。以下は 8.5.18 の挙動を自分の言葉で書いたものである。

**配置**

- キーの配列は長さ n + 1 (n は 2 の累乗)。最後の 1 個は「0 のキー (オブジェクトなら null)」専用である。
- 既定の作り方では n = 32、拡張のしきいは 24 である。
- 置き場所の最初の候補は、撹拌した値の下位ビット (n − 1 との論理積)。

**撹拌**

| キーの型 | 撹拌 |
|---|---|
| オブジェクト | hashCode に 0x9E3779B9 を掛け (32 ビットであふれを切り捨て)、その値と「符号なしで 16 ビット右へずらした値」の排他的論理和 |
| int | キーそのものに同じ処理 |
| long | キーに 0x9E3779B97F4A7C15 を掛け (64 ビット)、「符号なしで 32 ビット右へずらした値」との排他的論理和を取り、さらに「符号なしで 16 ビット右へずらした値」との排他的論理和を取る。下位 32 ビットを使う |

**入れる**

1. キーが 0 (null) なら専用の場所へ置く。
2. そうでなければ最初の候補から、添字を 1 ずつ増やしながら (末尾の次は 0) 空きを探す。途中で同じキーに当たれば値だけ置き換える。
3. 空きに置く。
4. 置く前の要素数がしきい以上だったら、表を作り直す。新しい n は「(置いた後の要素数 + 1) ÷ 0.75 の切り上げ」を 2 の累乗へ切り上げた値である。既定の表では 25 個目を入れた直後に、(25 + 1) ÷ 0.75 = 34.7 → 35 → n = 64 になる。

**作り直し**

古い配列を**添字の大きい方から**小さい方へ見て、見つけた順に新しい配列へ入れ直す (空き探しは同じ規則)。
0 のキーは専用の場所のまま移る。

**消す**

1. 要素を外し、その穴へ後ろの要素を詰める。添字を 1 ずつ進めながら、「本来の候補位置から見て、穴へ移しても探索がつながる」要素を穴へ動かし、動かした元を新しい穴にする。空きに当たったら終わる。墓標は置かない。
2. 消した後、n が最初の大きさより大きく、16 より大きく、要素数が「しきい ÷ 4」未満なら、n を半分にして作り直す。

**反復**

1. 0 のキーがあれば、それを最初に返す。
2. 続いて配列を添字 n − 1 から 0 へ**降順**に見て、埋まっている所を返す。

反復中に反復子で消した場合 (R4 が該当):

- 穴詰めで「配列の先頭側 (まだ見ていない) から末尾側 (もう見た) へ回り込んで動いた要素」は、別のリストに控えられ、配列を見終わった後に返される。
- どの要素もちょうど 1 回ずつ訪ねられる。
- 反復子で消したときは、表を半分にする作り直しは起きない。

**帰結**

- 反復順は、キーの値・入れた順・消した履歴・表の大きさで決まる。乱数や JVM の状態には依存しない (キーのハッシュ値が識別ハッシュでない限り)。
- BlockPos・long・int をキーにする表は、同じ操作列なら必ず同じ順になる。
- 逆に、同じ中身でも**作られ方が違えば順が違う**。作り直しが入ると入れ直しの順が変わるので、衝突している要素どうしの前後が入れ替わる。

### 4.5 個別の箇所の手順

#### R1 ダストの配布順 (DefaultRedstoneWireEvaluator#updatePowerStrength)

1. 空の HashSet を作る (入れ物 16 個)。
2. 自分の位置を入れる。
3. Direction の宣言順 (下・上・北・南・西・東) に、隣の位置を入れる。
4. HashSet の反復順に、各位置を中心とする 6 方向の近隣更新を出す。

7 要素では拡張も木構造化も起きない。同じ入れ物に入るのは最大でも数個で、その中は手順 2・3 の順である。
詳細と 42 件の届き先は → 06。

#### R2 ピストンの「空く位置」(PistonBaseBlock#moveBlocks)

1. 空の HashMap を作る (これを「空く位置の表」と呼ぶ)。
2. 押すリスト (toPush) を先頭から見て、各位置とその時点の状態を表に入れる。最大 12 個なので、要素数による拡張は起きない。
3. 壊すリストを末尾から処理する (ドロップ・空気への置き換え)。表には触れない。
4. 押すリストを末尾から処理する。各ブロックの**移動先**の位置を表から消し、移動先に moving_piston を置く。
5. 伸長なら、ヘッドの位置 (ピストンの正面) を表から消し、そこに moving_piston を置く。
6. 表に残ったキーが「何も入ってこない空く位置」である。**表の反復順に**、フラグ 82 で空気を書く (近隣更新も形状更新も出ない)。
7. もう一度**表の反復順に**、各位置について次の 3 つを出す。
   1. 元の状態の「間接の形状更新」(フラグ 2)。
   2. 空気の「6 方向の形状更新」(フラグ 2)。
   3. 空気の「間接の形状更新」(フラグ 2)。
8. 以降の近隣更新は、壊すリスト・押すリストの順で出す (表は使わない)。

表に残る数:

| 場面 | 残るキー |
|---|---|
| 一直線の伸長 | 0 個 (先頭はヘッドの位置、他は前のブロックの移動先なので全部消える) |
| 一直線の引き戻し | 1 個 (列の最も遠い位置) |
| スライム・ハチミツで枝分かれした構造 | 枝の本数ぶん。**2 個以上になると順が効く** |

残ったキーの順は「入れ物の番号の昇順。同じ入れ物の中は手順 2 で入れた順 (消したものを除く)」である。
手順 7 の形状更新を受けたオブザーバーは予約 tick を積む。積んだ順が予約順になり、同じ tick・同じ優先度の中の発火順になる (→ 02・08)。
よって枝分かれした構造では、オブザーバーの発火順が座標で変わりうる。[26.3 読解]

12 個で入れ物 16 個なので、「同じ入れ物に 9 個」が起きれば 9 個目で表が 32 個に広がる。
ハッシュ値 h が 0〜65535 か −65536〜−1 に収まる領域では、同じ入れ物に入るのは「x − y + z」が 16 を法として等しい位置で、これは互いに面で接しない。
ただしこれは領域の中だけの話である。h が 65536 の倍数の境をまたぐ所では、h の 16〜19 ビット目も変わるので、**面で接する 2 マスが同じ入れ物に入ることがある**。
例: (34, 222, 60) は h = 64576、その南の (34, 222, 61) は h = 65537 で、どちらも入れ物 0 に入る (式どおりに計算して確かめた)。
一直線に並べた 12 個では、同じ入れ物に入るのは最大 2 個だった (x・y・z の各軸、原点の周りの広い範囲を総当たり)。
つながった 12 個の構造で 9 個が同じ入れ物に入る配置は見つけていないが、「接しないから不可能」とは言えない。[要実機] 実装は一般の規則 (§4.2) をそのまま持てばよい。

#### R7・R8 読み込んだチャンクの BlockEntity の順

保存するとき (SerializableChunkData の作成):

1. ChunkAccess#getBlockEntitiesPos が、保留中の BlockEntity の位置の集まりを渡して HashSet を作る (大きさは §4.2 の「初期の大きさを指定して作る場合」)。
2. 実体のある BlockEntity の表 (fastutil) のキーを、その反復順 (§4.3) で HashSet に足す。
3. HashSet の反復順に、各 BlockEntity を保存用のリストへ足す。

読み込むとき (ChunkStatusTasks の FULL への昇格):

1. LevelChunk#runPostLoad が、保存されたリストの順に BlockEntity を作り、fastutil の表へ入れる。
2. チャンクを「読み込み済み」にする。
3. LevelChunk#registerAllBlockEntitiesAfterLevelLoad が、表の**値を反復順 (§4.3) に**見て、ゲームイベントのリスナーと ticker を登録する。
4. 予約 tick の入れ物を LevelTicks に登録する。

つまり読み直した後の BlockEntity の tick 順は、次の 3 段で決まる。

| 段 | 決めるもの |
|---|---|
| 保存前の fastutil の表の順 | 設置・撤去の履歴 |
| Java の HashSet の順 | 位置のハッシュ値と要素数 |
| 読み込み後の fastutil の表の順 | 上の順で入れ直した結果 |

3 段とも決定的である。写せば再現できる。ただし「保存前の表の順」は、その世界の全履歴に依存する。
構造ファイルや /setblock で作った直後の世界なら、履歴は設置順だけで決まる。[26.3 読解]

#### R10 エンティティの範囲検索の順

1. 検索範囲の箱を、x と z は 2 ブロック広げ、y は下へ 4 ブロック広げ、セクション座標に直す。
2. セクションの x を小さい方から順に見る。
3. 各 x について、キーが「その x の範囲」に入るセクションを、キーの符号つき昇順に見る。
   キーは z が上位・y が下位なので、z が先に並び、同じ z の中で y が並ぶ。
   z と y は下位ビットだけを詰めるので、**0 以上が先、負が後**になる。
4. セクションの中は、ArrayList の順 (= そのセクションに入った順)。別のセクションへ移ったエンティティは、移った先の末尾に入る。
5. 型を指定した検索は、型ごとのリストを使う。そのリストも同じく入った順である。

「最初の 1 体」を使う処理 (ボタンに刺さった矢・ディテクターレール上のトロッコなど) と、順に処理して途中で打ち切る処理 (ホッパーの吸い込み) で効く。中身は → 17。

#### R4 予約 tick のチャンクの順

1. LevelTicks#sortContainersToTick が、チャンクごとの「先頭の発火 tick」の表 (Long2LongOpenHashMap) を反復順 (§4.3) に見る。
2. 先頭の発火 tick が今の tick 以下で、入れ物があり、先頭の予約が期限内で、チャンクが tick の範囲内なら、その項目を**反復子で消し**、入れ物を優先度付きキューへ入れる。
3. 入れ物が無い・予約が空の項目も反復子で消す。先頭がまだ先なら値だけ書き直す。
4. キューの比較は、各入れ物の先頭の予約どうしを「優先度 → 予約順」で比べる。**発火 tick は比べない** (期限内のものしか入らないため)。

表の反復順が効くのは、この比較が同点のときだけである。
起動後に積んだ予約は予約順が一意 (0 以上の通し番号) なので、同点にならない。
保存から読み込んだ予約は、LevelChunkTicks#unpack がチャンクごとに「−(件数)」から 1 ずつ増やして振る。
よって同点は、別々のチャンクが読み込んだ予約どうしでだけ起こる (同じ優先度で、負の予約順が一致したとき。→ 02)。
そのときの結果は「二分ヒープに入れた順」と「ヒープの実装」の両方に依存する。[要実機]

もう 1 つ、表への入れ直しの順がある。
1 tick の件数上限 (→ 02) で取り切れなかった入れ物は、LevelTicks#rescheduleLeftoverContainers が表へ戻す。
このとき優先度付きキューを**そのまま反復する** (取り出し順ではなく、ヒープの内部配列の順)。
表へ入る順が変わると、衝突している項目どうしの前後が変わりうる (§4.3)。
上限に達したときだけの話で、かつ上の同点の条件が重ならない限り結果には出ない。[26.3 読解]

### 4.6 乱数

#### 4.6.1 Level の random の作り方

1. Level の初期化時に、RandomSource#create を引数なしで呼ぶ。
2. 種は「一意化の値 × 1181783497276652981 (呼ぶたびに更新) と、起動からのナノ秒の時刻との排他的論理和」である。
3. その種で LegacyRandomSource を作る。

ワールドの種 (seed) は**使わない**。同じワールドを同じ手順で開いても、列は毎回違う。
外から種を入れ直す手段も無い (/random が扱うのは 3.2 の「乱数列」で、Level の random ではない)。[26.3 読解: Level・RandomSource#create・RandomSupport#generateUniqueSeed]

LegacyRandomSource は、別スレッドから同時に使われると例外を投げる。乱数を引くのはサーバーのメインスレッドだけである。

#### 4.6.2 LegacyRandomSource の計算 (Rust で同じ列を作るための仕様)

状態は 48 ビットの整数 1 個である。

| 操作 | 手順 |
|---|---|
| 種を入れる | 状態 = (種 と 25214903917 の排他的論理和) の下位 48 ビット。正規乱数の控えを捨てる |
| 1 歩進めて b ビット取る | 状態 = (状態 × 25214903917 + 11) の下位 48 ビット。返す値は、状態を (48 − b) ビット右へずらし、32 ビットの符号つき整数にしたもの |
| nextInt (引数なし) | 32 ビット取る。1 歩 |
| nextInt (上限つき)・上限が 2 の累乗 | 31 ビット取り、上限を掛けて (64 ビットで) 31 ビット右へずらす。1 歩。**上限 1 でも 1 歩進む** |
| nextInt (上限つき)・それ以外 | 31 ビット取り、上限で割った余りを候補にする。「取った値 − 余り + (上限 − 1)」が 32 ビットであふれて負になる間は引き直す。普通は 1 歩 |
| nextLong | 32 ビットを 2 回取り、「1 回目を 32 ビット左へずらした値 + 2 回目 (符号つきのまま足す)」。2 歩 |
| nextBoolean | 1 ビット取り、0 でなければ真。1 歩 |
| nextFloat | 24 ビット取り、2 の −24 乗を掛ける。1 歩 |
| nextDouble | 26 ビットと 27 ビットを順に取り、「1 回目を 27 ビット左へずらした値 + 2 回目」に 2 の −53 乗を掛ける。2 歩 |
| nextGaussian | 極座標法。nextDouble を 2 回引いて −1〜1 の点を作り、原点からの距離の 2 乗が 1 以上か 0 なら引き直す。2 個できるうち 1 個を返し、もう 1 個を控える。次の呼び出しは控えを返すだけで乱数を引かない |
| triangle | 「中心 + 幅 × (1 回目の nextDouble − 2 回目の nextDouble)」。単精度版は nextFloat を 2 回 |
| fork | nextLong を種にして新しい乱数源を作る。2 歩 |

Mth の補助 (引く回数に注意):

| 関数 | 引く回数 |
|---|---|
| Mth#nextInt (最小・最大を含む) | 最小が最大以上なら**引かずに**最小を返す。そうでなければ nextInt を 1 回 |
| Mth#nextFloat・Mth#nextDouble | 最小が最大以上なら引かない。そうでなければ 1 回 |
| Mth#randomBetween・Mth#randomBetweenInclusive | 必ず 1 回 |
| Util#shuffle | 要素数 n に対し、上限 n・n − 1・…・2 の nextInt を順に 1 回ずつ (n − 1 回)。末尾から、引いた添字の要素と入れ替える |

XoroshiroRandomSource は 3.2 の「乱数列」で使う。状態は 64 ビット 2 個。
1 回の出力は「2 個の和を 17 ビット左回転したもの + 1 個目」で、その後 2 個を回転と排他的論理和で更新する。
回路の処理は直接は使わないので、手順の詳細は省く。必要になったら 26.3 の Xoroshiro128PlusPlus#nextLong を読む。

#### 4.6.3 毎 tick の消費 (回路と無関係に進む分)

| 相 | 消費 | 条件 |
|---|---|---|
| 天候 | タイマーが切れたときに次の長さを引く | advance_weather が真 (→ 01) |
| スポーン候補チャンクのシャッフル | 候補が n 個なら n − 1 回 | 凍結していない。プレイヤーが近いチャンクがある |
| 落雷の抽選 | 候補チャンクごとに上限 100000 の nextInt を 1 回 | 雨かつ雷のときだけ。そうでなければ引かない |
| 自然スポーン | 多数 | spawn_mobs が真 |
| 氷雪 | エンティティ tick の範囲のチャンクごとに、random_tick_speed 回、上限 48 の nextInt | random_tick_speed が 0 なら引かない |
| ランダム tick の中身 | 選ばれたブロックが引く分 | 同上 |
| エンティティ | 各エンティティは自分の乱数源を使う。Level の random を引くものもある | → 17 |

プレイヤーがいる世界では、シャッフルとスポーンが毎 tick 乱数を引く。
したがって「回路が引いた回数」だけを合わせても、実機の列とは合わない。

| 問い | 答え |
|---|---|
| 実機と同じ乱数の列を作れるか | **作れない**。種が時刻に依存し、外から入れられない。スポーンとシャッフルが毎 tick 引く |

### 4.7 randValue (ランダム tick の位置選び)

手順は → 01。数値の意味論だけ書く。

- 更新は 32 ビットの符号つき整数で行い、あふれを切り捨てる。
- 取り出しは算術右シフトで 2 ビット。上位ビットに符号が入るが、使うのは下位 4 ビットの組 3 つなので符号は効かない。
- 初期値は 26.3 ではスレッドごとの乱数から、1.21.1 では新しい乱数源から取る。どちらも外から決められない。[版差 1.21.1]

### 4.8 整数と浮動小数の意味論

Java の規則のうち、回路の式に出るものだけを挙げる。右の列は Rust での書き方である。

| Java の規則 | 出る場所の例 | Rust での書き方 |
|---|---|---|
| int の加減乗算は 32 ビットであふれを切り捨てる | 位置のハッシュ値・randValue・Mth#getSeed の「x × 3129871」 | wrapping_add・wrapping_mul。素の演算子はデバッグビルドで落ちる |
| long は 64 ビットで同じ | gameTime・発火 tick・予約順・線形合同法 | i64 の wrapping 演算。線形合同法は 48 ビットのマスクを掛ける |
| int どうしの乗算は、long へ広げる**前に**あふれる | Mth#getSeed は x の項だけ int で掛け、z の項は long で掛ける | 項ごとに型を合わせる |
| 整数の除算は 0 へ向けて切り捨てる | 「導火線 ÷ 4」「(a × 3 + b) ÷ 4」 | Rust の / と同じ |
| 剰余の符号は割られる数と同じ | 「gameTime を 200 で割った余り」 | Rust の % と同じ。Math.floorMod は rem_euclid |
| 右シフトは算術 (符号を保つ) と論理 (0 を入れる) の 2 種 | 撹拌は論理・座標の復元は算術 | 符号つき型の >> は算術。論理は符号なし型へ直してから |
| シフト量は型の幅で折り返す (int は下位 5 ビット、long は下位 6 ビット) | 「48 − b」などは範囲内 | wrapping_shl・wrapping_shr。範囲内なら素の演算子でよい |
| ブロック座標からセクション座標は算術右シフト 4 ビット | チャンクの判定 | >> 4 (負の座標で床になる) |
| 浮動小数から int への変換は 0 へ向けて切り捨て、範囲外は端の値、非数は 0 | Mth#floor・Mth#ceil の最後の変換 | Rust の as i32 と同じ規則 |
| long から int への変換は下位 32 ビット | 乱数の取り出し・撹拌 | as i32 |
| Mth#floor・Mth#ceil | 倍精度で床・天井を取ってから int へ | f64 の floor・ceil の後に as i32。単精度の引数は先に f64 へ広げる (値は変わらない) |
| Math.round (単精度) | 日照センサーの「明るさ × cos」 | 「0.5 を足して床」。ちょうど半分は**正の無限大の方**へ丸める。Rust の round は 0 から遠い方なので、負の値で違う。f64 に広げて 0.5 を足し floor する |
| float どうしの演算は単精度で行い、その場で丸める | コンテナの充填率の合計・重量感圧板の比 | f32 のまま計算する。f64 で計算してから丸めると結果が違う |
| int と float の演算は int を float へ直す | 「個数 ÷ 最大スタック数」 | as f32 してから割る |
| float と double の演算は double で行う | ターゲットブロックの「15.0 × …」は倍精度 | 式の中の定数の型を 1 つずつ確かめる |
| 複合代入は左辺の型へ暗黙に縮める | 「float へ double を足し込む」形 | 代入のたびに as f32 |
| Math.min・Math.max | 信号の飽和 (0〜15) | 整数は min・max。浮動小数は非数の扱いが違うが、回路の式に非数は出ない |
| Mth#clamp (整数) | 「最小と比べて大きい方、それと最大の小さい方」。最小が最大より大きくても例外にならず、**最大を返す** | 同じ順で min・max を書く。Rust の clamp は最小が最大より大きいと落ちる |
| Mth#lerpDiscrete | コンテナの信号。「始点 + 床 (割合 × (幅 − 1)) + (割合が 0 より大きければ 1)」 | f32 で掛けてから床 |
| Mth#frac | 「値 − 床 (値)」を倍精度で | ターゲットブロックの当たり位置 |
| Mth#sin・Mth#cos | 65536 要素の単精度の表を引く。角度 (倍精度の引数。単精度を渡すと先に広がる) に 10430.378350470453 を掛け、long へ **0 へ向けて**切り捨て、下位 16 ビットを添字にする。cos は掛けた値に倍精度で 16384.0 を足してから切り捨てる。表の中身は「添字 ÷ 10430.378350470453」の倍精度の sin を単精度へ丸めた値 | 表を同じ式で作って引く。標準の sin・cos を使うと境目で違う。版差あり (§6) |

アナログ値の式そのものは → 14。日照センサーは → 09。

**信号の値**

信号は int で持ち、ブロック状態の値域 (0〜15) へ入れるときに範囲を外れると例外になる。
各ブロックは入れる前に自分で 0〜15 に収めている。Rust では u8 で持ってよいが、
計算の途中 (減衰の「− 1」・コンパレーターの減算) は符号つきで行い、最後に 0 で止める。

**時刻**

gameTime・発火 tick は long である。遅延は int で受け、long へ広げて足す。
負の遅延も足せる (→ 02)。あふれは現実には起きない。

### 4.9 近隣更新の連鎖上限

手順とカウンタの数え方は → 04。本メモは値の出どころと境界だけを書く。

| 項目 | 内容 | 典拠 |
|---|---|---|
| 値の出どころ | サーバーの getMaxChainedNeighborUpdates が返す値を、ServerLevel の初期化が Level へ渡し、Level が CollectingNeighborUpdater を作るときに渡す | Level・ServerLevel |
| シングルプレイ (統合サーバー) | 基底クラスの固定値 1,000,000。変える手段は無い | MinecraftServer#getMaxChainedNeighborUpdates |
| 専用サーバー | server.properties の max-chained-neighbor-updates。既定 1000000 | DedicatedServer#getMaxChainedNeighborUpdates |
| 負の値 | 無制限 | CollectingNeighborUpdater#addAndRun |
| 数える範囲 | 最外の 1 件から、キューが空になるまで。tick の中で何度でも 0 に戻る | CollectingNeighborUpdater#runUpdates |
| 超えたとき | 新しい更新を捨てる。積み済みは走る。例外は投げない。エラーログを 1 回だけ出す | → 04 |
| クライアント側の Level | 別のインスタンスで別のカウンタ。サーバーの結果には関係しない | Level |

上限は「最外の呼び出し 1 回あたり」である。カウンタが 0 のときに来た更新が最外になり、その連鎖が終わると 0 に戻る。
予約 tick 1 件・ブロックイベント 1 件・プレイヤーの操作 1 回の中でも、連鎖の外から更新を 2 度出せば (例: 書き込みの後に、別の位置を中心とする近隣更新をもう 1 回出す)、それぞれが別の 1,000,000 件の枠を持つ。
「契機 1 件あたり 1 枠」ではない。[26.3 読解: CollectingNeighborUpdater#addAndRun・CollectingNeighborUpdater#runUpdates]
上限が 0 のときは、最初の 1 件から捨てる (カウンタ 0 が上限 0 以上なので)。

### 4.10 更新抑制の境界

「更新が届かなくなる」現象を、26.3 のコードの経路で分ける。

| 経路 | 26.3 での挙動 | エンジンの扱い |
|---|---|---|
| A. 連鎖上限に達する | 新しい更新を捨てて続行する。決定的 | 数えて捨てる。写す (→ 04) |
| B. 形状更新の残り回数が尽きる | 513 世代目の書き込みが形状更新を出さない。決定的 | 写す (→ 04) |
| C. 更新の処理の中で例外が出る | tick の中ならサーバーが止まる。**プレイヤーのパケット処理の中なら、ログに残して続行する** (メモリ不足が原因のときだけ止まる)。下記 | 対象外。到達したらエラーにする |
| D. 受け手のチャンクが tick の範囲外 | 更新そのものは届く。予約 tick・ブロックイベントが保留される (§4.11) | 前提を「全域が tick の範囲内」に固定する |

**C の経路** [26.3 読解]

1. NeighborUpdater#executeUpdate と NeighborUpdater#executeShapeUpdate は、処理の中で出たあらゆる例外とエラーを受け、クラッシュ報告つきの例外 (ReportedException) に包んで投げ直す。
2. CollectingNeighborUpdater#runUpdates は、例外で抜けるときもキューと追加リストを空にし、カウンタを 0 に戻す。**残りの更新は失われる**。
3. 例外が tick の中 (予約 tick・ブロックイベント・BlockEntity・エンティティ) で出た場合、途中で受ける所は無く、サーバーのメインループ (MinecraftServer#runServer) まで上がってクラッシュする。
4. 例外がプレイヤーのパケット処理の中で出た場合 (ブロックの設置・破壊・レバーの操作・コマンドなど):
   1. 26.3 のパケットは MinecraftServer#processPacketsAndTick が、tick の直前に PacketProcessor#processQueuedPackets でまとめて処理する。
   2. PacketProcessor が例外 (Exception の系統) を受ける。「クラッシュ報告つきの例外で、その直接の原因がメモリ不足のエラー」なら、そのまま投げ直す。受ける所は無いのでサーバーがクラッシュする。
   3. それ以外は、リスナーの onPacketError へ渡す。
   4. ServerCommonPacketListenerImpl#onPacketError は、まず親のインターフェースの実装を呼ぶ。ここで効くのは PacketListener の既定 (投げる) では**なく**、途中の ServerPacketListener が上書きした既定である。これは**エラーログ (「suppressing error」) を出すだけで、投げない**。
   5. 続いて MinecraftServer#reportPacketHandlingException が、例外を「抑えた例外」の記録へ足す (クラッシュ報告に載せるための控え)。
   6. 結果として**サーバーは動き続け、プレイヤーも切断されない**。手順 2 のとおり、その連鎖の残りの更新は失われたままである。
5. クラッシュした場合は、サーバーの停止処理が走り、世界は保存される。

つまり 26.3 では、プレイヤーの操作を契機とする連鎖の途中で例外が出ると、**握りつぶされて続行する**。これが「例外による更新抑制」の経路で、26.3 にも残っている。
止まるのは、原因がメモリ不足のエラーのときと、tick の中で出たときである。

継承の関係: ServerCommonPacketListenerImpl → ServerCommonPacketListener → ServerCookiePacketListener → ServerPacketListener → ServerboundPacketListener → PacketListener。
PacketListener#onPacketError の既定は投げるが、ServerPacketListener#onPacketError がそれを「ログだけ」に上書きしている。サーバー側のリスナーはすべてこの上書きを継ぐ。

スタックあふれのエラーが原因の場合: PacketProcessor が見るのはメモリ不足だけなので、26.3 では上の 4-4 へ進み、続行する。
ただし近隣更新はキューで回るので、連鎖の長さでスタックあふれは起こせない (下の「再帰の深さ」)。

**1.21.1 は続行の範囲がもっと広い** [版差 1.21.1]

- パケットの処理は PacketUtils#ensureRunningOnSameThread がサーバーのタスクとして積む。タスクは BlockableEventLoop#doRunTask の中で走る。
- メモリ不足以外の例外は、26.3 と同じく ServerPacketListener#onPacketError がログだけ出して握りつぶす。記録 (reportPacketHandlingException) は 1.21.1 には無い。
- メモリ不足が原因の例外は PacketUtils が投げ直すが、1.21.1 の BlockableEventLoop#doRunTask は**例外をすべて受けてログに出すだけ**で、投げ直さない。よって**これも続行する**。
- 26.2 以降の BlockableEventLoop#doRunTask は、「原因をたどるとメモリ不足かスタックあふれ」の例外だけ投げ直す (BlockableEventLoop#isNonRecoverable)。加えて 26.2 以降のパケットは doRunTask を通らず PacketProcessor が直接処理する。
- まとめると、近隣更新の中のメモリ不足を使う抑制は、1.21.1 では「続行」、26.2・26.3・26.4-pre-1 では「サーバーの停止」である。
- 包まれていない生のエラー (近隣更新の外で出たメモリ不足など) は、どの版でも Exception の系統ではないので受けられず、サーバーが止まる。

**26.4-pre-1 では切断が加わる** [版差 26.4-pre-1]

- ServerPacketListener が無くなり、onPacketError の宣言は PacketProcessor の中のインターフェースへ移った (既定の実装は無い)。
- ServerCommonPacketListenerImpl#onPacketError は、エラーログを出し、例外を記録し、**そのプレイヤーを切断する**。投げ直さない。サーバーは動き続ける。
- メモリ不足が原因の例外だけは、PacketProcessor が今までどおり投げ直す (サーバーが止まる)。
- 26.3 との違いは「操作したプレイヤーが切断される」ことだけである。残りの更新が失われて続行する点は同じ。

**例外を起こせる組み合わせが実在するか**

26.3 のブロックのコードに、プレイヤーが意図して例外を起こせる組み合わせが残っているかは読んでいない。
既存資料が挙げる型変換の例外 (シュルカーボックスの中身の入れ替え) が直っているかも、本メモでは確かめていない。[要実機]
経路 (握りつぶして続行) があることと、実際に例外を起こせることは別である。

**再帰の深さ**

近隣更新と形状更新はキューで回るので、連鎖の長さで呼び出しの深さは増えない。
ブロックの処理の中の再帰は、どれも上限つきである (パワードレールの探索 8・ピストンの構造 12 など。→ 15・13)。
スタックあふれに至る経路は見つけていない。[26.3 読解]

### 4.11 チャンクの読み込み状態が tick に与える影響

相ごとの条件の表は → 01。ここでは決定性に関わる点だけを足す。

| 事象 | 26.3 の挙動 | 典拠 |
|---|---|---|
| 未読み込みのチャンクの位置を Level#getBlockState で読む | **その場で同期的に読み込む (無ければ生成する)**。「unknown」チケット (レベル 33・寿命 1 tick) が付く | Level#getBlockState・ServerChunkCache#getChunk |

## 5. 端の場合と落とし穴

1. **HashSet の順は「座標の昇順」ではない**。入れ物の番号は「x − y + z」に近い値で決まり、ハッシュ値が負になる領域では逆向きになる (§4.2)。
2. **同じ回路でも、平行移動で順が変わる**。ハッシュ値が 0〜65535 の領域では、x・z を 1 増やすと番号が 1 増え、y を 1 増やすと 1 減る (16 で折り返す)。全体を同じだけずらしても、折り返しの位置が変わるので入れ物の昇順は変わる。ハッシュ値が 65536 の境を越えると、16〜19 ビット目との排他的論理和が変わり、規則そのものが変わる。
3. **Java の HashMap は 12 個以下でも拡張しうる**。同じ入れ物に 9 個入ると、入れ物数 64 未満の表は 2 倍になる (§4.2・§4.4)。「12 個以下なら入れ物は 16 個」とは言い切れない。
4. **Java の HashMap は消しても縮まない。fastutil は縮む**。fastutil は消したときに穴詰めで要素が動き、要素数が減ると表を半分に作り直す。
5. **fastutil の反復は添字の降順**。昇順で写すと逆になる。0 のキー (null) は必ず先頭である。
6. **fastutil の連結つきの型は、入れ直しても位置が変わらない**。ブロックイベントの重複が後ろへ回らないのはこのためである。
7. **ピストンの「空く位置」の順は、一直線の構造では効かない**。残るキーが 0 個か 1 個だからである。枝分かれした構造でだけ効く (§4.5)。
8. **ピストンの表の 1 周目は空気を書くだけで更新を出さない**。順が観測に出るのは 2 周目の形状更新である。
9. **上限 1 の nextInt も乱数を 1 歩進める**。ディスペンサーのスロットが 1 個でも、ホッパーの上のトロッコが 1 台でも、列は進む。
10. **Mth#nextInt は最小が最大以上なら乱数を引かない**。Mth#randomBetweenInclusive は必ず引く。名前が似ているが違う。
11. **音の種は random を使わない。音の高さは使う**。ピストン・ドアの音は列を 1 歩進め、音符ブロックは 2 歩進める。
12. **nextGaussian は 2 回に 1 回しか乱数を引かない**。控えは種を入れ直すと消える。
13. **Level の random はワールドの種と無関係**。同じ種のワールドでも列は毎回違う。
14. **エンティティは自分の乱数源を持つ**。アイテムの初速の一部は Level の random、一部はエンティティの random である。
15. **連鎖上限は深さではなく件数**。形状更新の 512 は深さである。別のカウンタである (→ 04)。
16. **統合サーバーでは連鎖上限を変えられない**。上限の検証は専用サーバーで行う。
17. **例外による更新抑制の経路は、どの版にも残っている** (§4.10)。プレイヤーのパケット処理の中で出た例外は、ServerPacketListener#onPacketError がログだけ出して握りつぶし、サーバーは続行する。PacketListener の既定 (投げる) だけを見ると「止まる」と読み違える。tick の中で出た例外はサーバーを止める。メモリ不足が原因のときは、1.21.1 は続行、26.2 以降は停止。26.4-pre-1 は続行に加えてプレイヤーを切断する。
18. **未読み込みのチャンクは、読むだけで読み込まれる**。01 の表の「読み込み済みなら届く」は、正確には「届くときに読み込む」である。[26.3 読解]
19. **Math.round と Rust の round は負のちょうど半分で違う**。
20. **整数の clamp は、最小が最大より大きいとき最大を返す**。26.4-pre-1 では標準の関数に置き換わり、この場合は例外になる (§6)。
21. **予約 tick の同一性のハッシュは起動ごとに変わるが、順には出ない** (§3.1)。写す必要はない。
22. **木構造になった HashMap の入れ物は、識別ハッシュで順が変わりうる**。要素の多い集合 (爆発・保存) だけの話で、ダストとピストンには関係しない。

### 6.2 [版差 1.21.1] Mth#sin・Mth#cos

1.21.1 は角度を単精度のまま単精度の乗数と掛け、int へ切り捨ててから下位 16 ビットを取る。
26.2 以降は倍精度で掛け、long へ切り捨てる。
表の中身の式も書き方が違う (1.21.1 は「添字 × 円周率 × 2 ÷ 65536」、26.3 は「添字 ÷ 10430.378350470453」)。
境目の角度では添字が 1 ずれうる。日照センサーの出力の切り替わりが 1 tick ずれる可能性がある。[要実機] (→ 09)

### 6.3 [版差 26.4-pre-1] Mth#sin・Mth#cos と clamp

- sin・cos は添字の計算に 0.5 を足す。負の角度は正に直して引く。表の 0 度・90 度・180 度・270 度を 0・1・0・−1 に上書きする。日照センサーの境目が 26.3 とずれうる。[要実機]
- 整数の clamp が標準の関数になった。標準の関数は「最小が最大より大きい」と例外を投げる。
  26.4-pre-1 の LecternBlockEntity は、上限側を「ページ数 − 1 と 0 の大きい方」にして、この場合を避けている。
  回路の式で最小が最大を超える所は、読んだ範囲では無い。

### 6.4 [版差 26.4-pre-1] 集合型の書き方

DefaultRedstoneWireEvaluator・EuclideanGameEventListenerRegistry・ClassInstanceMultiMap で、guava の補助を使わず Java 標準の型を直接作る書き方に変わった。
作られる型と大きさは同じである。挙動は変わらない。

ServerExplosion から、プレイヤーへのノックバックを覚える HashMap が消えた。爆発で壊す位置の集合は同じである (→ 17)。

### 6.5 [版差 1.21.1] [版差 26.4-pre-1] パケット処理中の例外

§4.10 のとおりである。diff で確かめた点だけ書く。

| 版 | ServerPacketListener#onPacketError | ServerCommonPacketListenerImpl#onPacketError | BlockableEventLoop#doRunTask |
|---|---|---|---|
| 1.21.1 | 有る (ログだけ) | 上書きしない | 例外を全部受けてログだけ |
| 26.2・26.3 | 有る (ログだけ) | 親を呼んでから例外を記録する | メモリ不足・スタックあふれが原因の例外だけ投げ直す |

エンジンの既定の対象 (26.3) では、プレイヤーの操作を契機とする連鎖は「例外が出たら残りを捨てて続行」が実機の挙動である。
エンジンは例外を起こすブロックを持たないので、この経路は到達しない前提でよい (§7.4)。

### 6.6 ライブラリの版

fastutil は 8.5.12 (1.21.1) と 8.5.18 (26.3) で版が違う。§4.3 の規則は 8.5.18 で確かめた。

## 7. Rust で実装するときの要点

### 7.1 データ構造

| 用途 | 持ち方 |
|---|---|
| R1・R2・R8 | 「Java の HashMap の写し」を 1 つ作る。入れ物の配列と、各入れ物の中の順つきの列を持つ。入れる・消す・拡張 (しきいと 9 個目の両方)・反復を §4.2 のとおりに書く。木構造は実装せず、到達したらエラーにする |
| R1 だけを速くしたい場合 | 7 要素・入れ物 16 個に固定した専用の関数でよい。番号を計算し、(番号, 入れた順) で安定に並べる |
| R7・R11・R4 | 「fastutil の開番地の写し」を 1 つ作る。キーの型ごとに撹拌を差し替える。読み込み直しを扱わないなら不要 |
| R3・R9・R13 | 挿入順を保つ集合 (索引つきの連結リスト、または indexmap 相当)。入れ直しで位置を動かさないこと |
| R5 | 比較キー (発火 tick, 優先度, 予約順) の二分ヒープか B 木 |
| R6 | Vec。除去は印を付けて、反復のときに詰める (→ 01) |
| R10 | セクションのキーの B 木と、セクションごとの Vec |
| エンジン内部の作業用の表 | 反復しないなら何でもよい。**反復するなら Rust の標準の HashMap を使わない** (実行ごとに順が変わる) |

### 7.2 乱数

- LegacyRandomSource を u64 の状態 1 個で持つ。4.6.2 の表を 1 行ずつ関数にする。正規乱数の控えも状態に含める。
- ワールドごとに 1 個。種はエンジンの引数で受ける。スナップショットに状態を含める。
- 4.6.4 の表の箇所で、同じ順に同じ回数だけ引く。音だけに使う分も引く (引かないなら、引かないと文書に書く)。
- randValue は別の u32 の状態として持つ。
- エンティティを実装するなら、エンティティごとの乱数源を別に持つ。種の決め方はエンジンが決める (実機と合わせる意味が無い)。
- テストの期待値に乱数の列の一致を含めない。含めるのは「引く回数」と「結果の集合」である。

### 7.3 数値

- 座標は i32、時刻は i64、信号は計算中は i32。
- ハッシュ値と線形合同法は wrapping 演算で書く。
- 単精度の式は f32 で書く。f64 で書いて最後に丸めない。
- 丸めは Math.round の規則を関数にして使う。
- 三角関数は表を同じ式で作る。版ごとに式が違うので、版を引数にする。

### 7.4 上限と例外

- 連鎖上限はエンジンの設定値にする (既定 1,000,000)。負は無制限。
- 超えたら捨てて続ける。最初に捨てた座標を 1 回だけ記録する。
- 例外の経路 (§4.10 の C) は「エンジンのエラー」として返す。続行しない。実機はプレイヤーの操作の中なら残りの更新を捨てて続行するが、エンジンのブロックのコードは例外を起こさない前提で書くので、到達したらバグである。例外による更新抑制を再現する対象にはしない (docs/research/12_update-suppression.md の結論と同じ)。
