## 2. 全体像

### 2.1 ダストの 3 つの仕事

ダストの挙動は、次の 3 つに分かれる。互いに別の契機で動く。

| 仕事 | 契機 | 何をするか |
|---|---|---|
| 形状 (4 方向の接続) の維持 | 形状更新 (隣の 6 マスと、斜め上下のダストから届く) | north / east / south / west を書き換える。電力は計算しない |
| 電力 (power) の計算 | 近隣更新・設置・除去 | 評価器が power を書き、周りへ近隣更新を出す |
| 信号の出力 | 他のブロックからの問い合わせ | 真下と、接続している水平方向へ power を返す。接続はその場で計算し直す |

要点は次の 4 つ。

1. **形状更新は電力の再計算を起こさない**。形状の書き込みは近隣更新を出さない (フラグ 1 が落ちている)。
2. **電力の再計算は近隣更新でだけ起きる** (設置と除去のフックも近隣更新と同じ評価器を呼ぶ)。
3. **信号の出力は保持している形状を見ない**。問い合わせのたびに周りを見て接続を計算し直す。保持値が効くのは「点かどうか」だけ。
4. 評価器は 2 つある。既定の世界は既定の評価器を使う。実験機能 redstone_experiments を有効にした世界だけが実験の評価器を使う。

### 2.2 既定の評価器の流れ (概略)

1. ダストが近隣更新を受ける。
2. 支えが無ければ、アイテムを落として自分を消す。ここで終わる。
3. 支えがあれば、目標の電力を計算する (周りのブロックからの信号と、隣のダストの値 − 1 の大きい方)。
4. 今の電力と同じなら何もしない。
5. 違えば、フラグ 2 で power を書く。この書き込みは形状更新を出す (オブザーバーが見る)。近隣更新は出さない。
6. 「自分と隣 6 マス」の 7 か所を HashSet に入れ、その反復順で、各か所の周り 6 マスへ近隣更新を出す (7 × 6 = 42 件)。
7. 近隣更新は深さ優先で処理される。隣のダストは 1 の手順を再帰的に繰り返す。途中の値が世界に書かれる。

### 2.3 実験の評価器の流れ (概略)

1. 起点のダストから、下げる待ち行列 → 上げる待ち行列の順に、網の全ダストの新しい値を表の上で決める。世界には書かない。
2. 表の登録順に、値が変わったダストだけをフラグ 2 | 128 で書く。
3. 表の登録順に、各ダストから「接続している水平方向と真下」のブロックへ近隣更新を出す。導体ならその先の 5 マスにも出す。
4. ダスト同士の近隣更新は無視される。

## 3. 状態とデータ

### 3.1 blockstate

| プロパティ | 値域 | 既定 | 意味 |
|---|---|---|---|
| north | up / side / none | none | 北側の接続 |
| east | up / side / none | none | 東側の接続 |
| south | up / side / none | none | 南側の接続 |
| west | up / side / none | none | 西側の接続 |
| power | 0〜15 | 0 | 電力 |

状態の総数は 3^4 × 16 = 1296。プロパティの登録順は north, east, south, west, power [26.3 読解: RedstoneWireBlock#createBlockStateDefinition]。

RedstoneSide は up・side・none の 3 値。「接続している」は none 以外のこと [26.3 読解: RedstoneSide#isConnected]。

### 3.2 用語

| 用語 | 定義 |
|---|---|
| 点 (dot) | 4 方向とも none |
| 十字 (cross) | 4 方向とも接続 (up か side) |
| 十字の基準状態 | 4 方向とも side・power 0 の状態 (RedstoneWireBlock が生成時に作って持つ) |
| 生の接続 | 周りのブロックだけから決まる接続。自動の延長を掛ける前 |

### 3.3 ブロックに持つ値 (blockstate の外)

| 値 | 持ち主 | 内容 |
|---|---|---|
| shouldSignal | RedstoneWireBlock のインスタンス (全世界で 1 個) | 既定は真。ダストが周りのブロックの信号を読む間だけ偽にする |
| evaluator | RedstoneWireBlock のインスタンス | 既定の評価器を 1 個持つ。状態を持たない |
| 実験の評価器 | 呼び出しごとに新しく作る | 2 本の待ち行列と 1 個の表を持つ。1 回の計算で使い捨て |

BlockEntity は無い。予約 tick もブロックイベントも使わない。ランダム tick も無い。

## 4. 処理の詳細

以下、ダストの位置を p と書く。p の北・東・南・西を「横」、p の真上を「上」、真下を「下」と書く。

### 4.1 接続先になるか (shouldRedstoneWireConnectTo)

26.3 では、接続先かどうかを各ブロックのフックが答える [26.3 読解: BlockBehaviour#shouldRedstoneWireConnectTo]。
引数の「向き」は、**ダストから相手へ向かう方向**。向きが無い (null) 問い合わせもある。

| 相手 | 向きあり | 向き無し | 典拠 |
|---|---|---|---|
| ダスト | 真 | 真 | RedstoneWireBlock#shouldRedstoneWireConnectTo |
| リピーター | facing が向きと同じか、その逆のとき真 | 偽 | RepeaterBlock#shouldRedstoneWireConnectTo |
| オブザーバー | facing が向きと同じときだけ真 | 偽 | ObserverBlock#shouldRedstoneWireConnectTo |
| それ以外 | 信号源なら真 | 偽 | BlockBehaviour#shouldRedstoneWireConnectTo |

補足。

- リピーターは前後の軸にあるダストとだけ接続する。横には接続しない。
- オブザーバーの facing は観測面の向き。facing が「ダスト → オブザーバー」と同じとは、観測面がダストの反対側にあること。つまり **ダストは出力面 (背面) にだけ接続する**。
- コンパレーターは上書きしていない。信号源なので 4 面とも接続する。
- 信号源の一覧は → 05_signals-and-block-properties.md。信号源かどうかは blockstate で決まる (ブロックごとに実装が違う)。
- 向き無しの問い合わせは、斜め上と斜め下の相手を調べるときに使う。真を返すのはダストだけ。つまり **斜めに接続する相手はダストだけ**。
- 26.3 でこのフックを上書きしているのは上の 3 クラスだけ (全クラスを検索して確かめた)。

[実機 1.21.1: wire-connect-detector-rail-lectern] 検知レールと書見台は信号源なので接続する。

### 4.2 1 方向の接続 (RedstoneWireBlock#getConnectingSide)

入力は p・水平の方向 d・「上へ接続できるか」。
「上へ接続できるか」は、p の真上のブロックが導体でないこと。

横のブロックを n = p + d とする。

1. 上へ接続できるなら、次を調べる。
   1. n の上にダストを置けるか。条件は「n がトラップドア (状態を問わない)」または「n の上面が頑丈」または「n がホッパー」。
   2. n の真上がダストか (向き無しの問い合わせ)。
   3. 1 と 2 がともに真なら、ここで決まる。n の、p 側の側面が頑丈なら **up**。頑丈でなければ **side**。
2. 1 で決まらなければ、次のどちらかが真なら **side**。どちらも偽なら **none**。
   - n が接続先である (向き d の問い合わせ)。
   - n が導体でなく、かつ n の真下がダストである (向き無しの問い合わせ)。

読み方の要点。

- 上りの判定が先。n が接続先でも、n の真上にダストがあれば up になる (例: レッドストーンブロックやターゲットの上のダスト)。
- 上りは、n が導体かどうかを見ない。ガラス・上付きハーフ・ホッパーの上のダストにも接続する。
- up と side の違いは見た目 (壁を登る線を描くか) だけ。どちらも「接続している」。ハーフ・ホッパー・階段の一部は側面が頑丈でないので side になる。
- 上りは、p の真上が導体だと切れる。下りは、n が導体だと切れる。**どちらも「下の段のダストの真上」のマスを見ている**。だから関係は対称で、上段のダストが支えられている限り、片方だけが接続することは無い。
- トラップドアは開いていても「置ける」と数える。ただしトラップドアの真上にダストが実在できるのは、上面が頑丈な状態 (上付きで閉じている) のときだけ。開いた後にダストが残る瞬間があるかは [要実機]。

落とし穴。「上へ接続できるか」の導体判定は、真上のブロックの状態に対して **p の座標** を渡している (真上の座標ではない) [26.3 読解: RedstoneWireBlock#getConnectingSide・RedstoneWireBlock#getMissingConnections]。
導体判定が座標に依存するブロックは通常無いので、結果は変わらない。Rust では真上の状態だけで判定してよい。

### 4.3 4 方向の接続と自動の延長 (RedstoneWireBlock#getConnectionState)

入力は p と、今の状態 (保持値)。

1. 入力の状態が点かどうかを覚える。
2. 4 方向を none にした状態 (power は入力のまま) から、北・東・南・西の順に 4.2 で生の接続を求める [RedstoneWireBlock#getMissingConnections]。
3. 1 が真で、2 の結果も点なら、点のまま返す (**点の保持**)。
4. そうでなければ、2 の結果から次の 2 つの真偽を先に求める。
   - 南北が空 = 北も南も非接続
   - 東西が空 = 東も西も非接続
5. 次の順に延長する。判定に使う真偽は 4 で求めた値のまま (途中で変えない)。
   1. 西が非接続で南北が空なら、西を side にする。
   2. 東が非接続で南北が空なら、東を side にする。
   3. 北が非接続で東西が空なら、北を side にする。
   4. 南が非接続で東西が空なら、南を side にする。

結果の表。

| 生の接続 | 結果 |
|---|---|
| 0 本 (入力が点) | 点のまま |
| 0 本 (入力が点でない) | 十字 (4 方向 side) |
| 1 本 | その反対側も side になり、直線になる |
| 2 本 (向かい合わせ) | そのまま (直線) |
| 2 本 (角)・3 本・4 本 | そのまま |

[実機 1.21.1: dust-cross-powering] 孤立したダストは十字になり、水平 4 方向へ給電する。
[実機 1.21.1: dust-line-powering] 接続 1 本のダストは直線になり、延長端へ給電し、直角方向へは給電しない。

### 4.4 設置時の状態 (RedstoneWireBlock#getStateForPlacement)

プレイヤーがアイテムで置くときは、十字の基準状態を入力にして 4.3 を呼ぶ。
入力が点でないので、孤立していれば十字になる。power は 0。

### 4.5 支え (RedstoneWireBlock#canSurvive)

真下のブロックが次のどちらかなら置ける。

- 上面が頑丈 (満杯の面を持つ)。
- ホッパーである。

上面が頑丈なブロックの例は、満杯の立方体・上付きハーフ・上下逆の階段・上付きで閉じたトラップドア・ガラス・グロウストーンなど。一覧は → 05_signals-and-block-properties.md。

支えを失ったダストが消える経路は 2 つある。

| 経路 | 契機 | 手順 | 落とす物 |
|---|---|---|---|
| 近隣更新 | RedstoneWireBlock#neighborChanged で canSurvive が偽 | アイテムを落とす → Level#removeBlock (フラグ 3) | 落とす |
| 形状更新 | RedstoneWireBlock#updateShape に下から届き、形状更新が運んできた下の状態が支えにならない (世界の今の真下ではない。4.6) | 空気を返す → Block#updateOrDestroy → Level#destroyBlock (フラグ 3) | 落とす (下の注) |

注。Block#updateOrDestroy は「受け取ったフラグに 32 があれば落とさない」と判定する。
しかし Level#setBlock は、形状更新へ渡す前にフラグから 1 と 32 を落とす [26.3 読解: Level#setBlock]。
だから Level#setBlock から始まる形状更新では、元の書き込みにフラグ 32 があっても **アイテムは落ちる**。
落ちないのは、フラグ 32 を持ったまま Block#updateOrDestroy を直接呼ぶ経路だけ (構造物の配置など。ダストの担当外)。

下のブロックがフラグ 3 で変わると、近隣更新が先に届く (Level#setBlock はフラグ 1 の近隣更新を形状更新より先に出す)。だから通常は近隣更新の経路で消える。
下のブロックがフラグ 2 だけで変わると、形状更新の経路で消える。
実験機能が有効で、近隣更新の送り主がダストのときは、支えの確認もしない (4.11)。

### 4.6 形状更新 (RedstoneWireBlock#updateShape)

呼ばれる契機は、隣のブロックの書き込み (フラグ 16 が無いもの) と、4.7 の斜めの通知。
引数の「方向」は、p から変化した隣へ向かう方向。

| 方向 | すること |
|---|---|
| 下 | 形状更新が運んできた「隣の状態」が支えにならなければ空気を返す。支えになれば今の状態のまま (下の「下の段で見る状態」) |
| 上 | 今の状態を入力にして 4.3 を呼び、その結果を返す (全部を計算し直す。点の保持が効く) |
| 水平 d | 下の手順 |

水平 d の手順。

1. 4.2 で d の方向の生の接続 s を求める。
2. 「s が接続か」と「保持値の d が接続か」が同じで、かつ保持値が十字でないなら、保持値の d だけを s に置き換えて返す (up と side の入れ替え、または none のまま)。
3. それ以外なら、「十字の基準状態に今の power を入れ、d を s にした状態」を入力にして 4.3 を呼ぶ。入力が点でないので、点の保持は効かない。全部を計算し直す。

下の段で見る状態 [26.3 読解: RedstoneWireBlock#updateShape・RedstoneWireBlock#canSurviveOn・NeighborUpdater#executeShapeUpdate・CollectingNeighborUpdater#shapeUpdate・BlockBehaviour.BlockStateBase#updateNeighbourShapes]。

- 支えの判定に使うのは、**形状更新が運んできた隣の状態**である。世界の真下を読み直さない。
- 判定の中身は 4.5 と同じ。運ばれた状態の上面が頑丈 (FULL) か、運ばれた状態のブロックがホッパーなら支えになる。
- 運ばれる状態は、真下の書き込みが形状更新を積んだ時点の「新しい状態」(Level#setBlock が書いた状態) である。
  積んでから走るまでに真下がまた書き換わっても、運ばれた状態は変わらない (→ 04 §4.6・§5.5)。
- 世界から読むのは 2 つだけである。
  1. 受け手 (ダスト) 自身の状態。走る時点で読む。もうダストでなければ、ダストの updateShape は呼ばれない。
  2. 動的形状のブロックの面の形。運ばれた状態に、真下の座標の今の世界を合わせて計算する (→ 05 §4.7.4)。動的形状でないブロックは、運ばれた状態だけで決まる。
- 近隣更新の経路 (4.11 の手順 2・3 → 4.5) は逆で、**世界の今の真下**を読む。

| 経路 | 支えを判定する状態 | 典拠 (26.3) |
|---|---|---|
| 近隣更新 | 世界の今の真下 | RedstoneWireBlock#neighborChanged → RedstoneWireBlock#canSurvive |
| 下からの形状更新 (真下の書き込みが積んだもの) | 運ばれた状態 (積んだ時点の真下) | RedstoneWireBlock#updateShape → RedstoneWireBlock#canSurviveOn |
| /setblock が書く前に直す段 (4.14.1 の手順 1) | 呼ぶ時点で世界から読んだ真下 (積まずにその場で渡すので、今と同じ) | Block#updateFromNeighbourShapes |
| 斜めの通知 (4.7) | 判定しない (方向が水平なので、下の段を通らない) | RedstoneWireBlock#updateIndirectNeighbourShapes |

2 つの読み方で結果が違うのは、積んだ更新が走らない間 (1 つの neighborChanged やフックの中。→ 04 §5.5) に真下が 2 回以上書き換わり、途中の状態が支えにならないときである。

- 例。真下を「石 → 空気 → 石」と続けて書く (どちらもフラグ 16 無し)。形状更新は書き込みごとに積まれ、1 件目は空気を、2 件目は石を運ぶ。
  1 件目が走る時点で、世界の真下はもう石に戻っている。それでもダストは運ばれた空気で判定し、**消える** (アイテムを落とす。4.5 の注)。
  2 件目が走る時点では受け手がダストでないので、ダストの処理は走らない。「世界の今の真下」で判定する実装では、ダストが残ってしまう。
- 逆の例。真下を「石 → 空気」と続けて書く。どちらの読み方でも消えるが、消える時点が違う。運ばれた状態で判定すると、1 件目 (石) では残り、2 件目 (空気) で消える。「世界の今の真下」で判定する実装では、1 件目で消えてしまう。
- 形状更新を積んでから走るまでに真下が書き換わらなければ、運ばれた状態と世界の今の真下は同じである。差は出ない。最上位から呼ばれた 1 回の書き込みは、これに当たる。
- 26.3 のどの素子が、1 回の処理の中で同じマスを続けて書くかは、ここでは洗い出していない。そういう素子 (ピストンほか) を入れる時に、その素子のメモで書き込みの列を確かめる。

返した状態が今と違えば、Block#updateOrDestroy が書く。フラグは「元の書き込みのフラグから 1 と 32 を落としたもの」。
元がフラグ 3 なら 2 で書く。**近隣更新は出ない**。だから電力の再計算も、給電先への通知も起きない。
この書き込み自体は、また隣 6 マスへ形状更新を出す (連鎖の深さの上限は 512。→ 04_set-block-and-updates.md)。

読み方の要点。

- 手順 2 は「その方向だけ」を直す。他の 3 方向の保持値には触れない。保持値が実情とずれていても、その方向の形状更新が来るまで直らない。
- 手順 2 の条件から十字が外れているのは、十字が「延長の結果」かもしれないため。十字のときは必ず全部を計算し直す。
- 直線のダストの横に接続先が現れると、手順 3 で角になる。延長で立っていた反対側が消える。**このとき、消えた側のブロックには何も届かない** (MC-3703)。
  [実機 1.21.1: dust-reshape-stale-target] ランプもピストンも、別の近隣更新が来るまで古い状態のまま残る。

### 4.7 斜めの通知 (RedstoneWireBlock#updateIndirectNeighbourShapes)

Level#setBlock は、フラグ 16 が無ければ次の順で形状更新を出す。

1. 古い状態の斜めの通知
2. 新しい状態から隣 6 マスへの形状更新 (西・東・北・南・下・上)
3. 新しい状態の斜めの通知

ダストの斜めの通知は次のとおり。対象の状態 (古い方か新しい方) の保持値を使う。

1. 北・東・南・西の順に、次を調べる。
2. その方向の保持値が none なら飛ばす。
3. その方向の横のブロックがダストなら飛ばす。
4. 横の 1 段下がダストなら、そのダストへ形状更新を送る。
5. 横の 1 段上がダストなら、そのダストへ形状更新を送る。

送る形状更新の中身。

| 項目 | 値 |
|---|---|
| 受け手 | 斜め下 (または斜め上) のダスト |
| 方向 | p から見た方向の逆 (受け手から見て p の側) |
| 「隣の位置」 | 受け手からその方向へ 1 マス = p の真下 (または真上) |
| 「隣の状態」 | その位置の今の状態 |
| フラグ・深さの上限 | 元の書き込みから引き継ぐ |

受け手は水平方向の形状更新として処理する (4.6)。受け手の 4.2 は p を斜めに見つけるので、接続が正しく直る。
「隣の状態」は受け手の判定に使われない (水平の処理は自分で周りを読む)。

power だけの書き込みでも 1〜3 は走る。受け手の保持値が実情と合っていれば、結果は変わらず、書き込みは起きない。
保持値が実情とずれたダスト (5.2) は、隣のダストの power が変わっただけでも、このとき形が直ることがある (隣 6 マスへの形状更新も同じ)。

形状更新も近隣更新と同じ CollectingNeighborUpdater の上で配られる [26.3 読解: Level#neighborShapeChanged・CollectingNeighborUpdater#shapeUpdate]。
近隣更新の処理中に出た形状更新は、その場では走らず、出た順に積まれる (4.12.3)。

### 4.8 信号の出力 (RedstoneWireBlock#getSignal・#getDirectSignal)

引数の「方向」は、**問い合わせるブロックからダストへ向かう方向** (SignalGetter の呼び方による)。

RedstoneWireBlock#getSignal の手順。

1. shouldSignal が偽なら 0。
2. 方向が下なら 0 (問い合わせ主はダストの真上にいる)。
3. power が 0 なら 0。
4. 方向が上なら power (問い合わせ主はダストの真下にいる)。
5. 水平なら、今の状態を入力にして 4.3 を呼ぶ。その結果で「方向の逆」の側が接続なら power。非接続なら 0。

RedstoneWireBlock#getDirectSignal は、shouldSignal が偽なら 0。真なら getSignal と同じ値。

| 問い合わせ主の位置 | 方向 | 結果 |
|---|---|---|
| ダストの真下 | 上 | power |
| ダストの真上 | 下 | 0 |
| ダストの水平隣 (ダストから見て d の側) | d の逆 | 4.3 の結果で d が接続なら power。非接続なら 0 |

読み方の要点。

- 手順 5 は保持値の形状を使わない。周りから計算し直す。保持値が効くのは点の保持だけ。
  例: 保持値が「北だけ side」で周りに何も無いダストは、問い合わせでは十字として答える。
- ダストは真下と接続方向のブロックへ「強い信号」を出している (getDirectSignal が power を返す)。
  導体はそれを受けて周りへ信号を出す (SignalGetter#getSignal は導体について getDirectSignalTo との大きい方を返す)。
- ただし他のダストが電力を計算している間は shouldSignal が偽なので、ダスト由来の信号は一切見えない。
  これが「ダストが充電した導体は、他のダストに給電しない」の実体。弱い信号という別の経路は無い。
- shouldSignal が偽の間は RedstoneWireBlock#isSignalSource も偽になる。計算は 1 回の呼び出しの中で終わるので、外からこの状態は見えない。

[実機 1.21.1: dust-cross-powering] 真上のランプは点かず、足元のランプは点く。
[実機 1.21.1: dust-block-repeater] ダストが指す導体の充電を、リピーターは入力として読む。

### 4.9 周りのブロックから読む値 (RedstoneWireBlock#getBlockSignal)

1. shouldSignal を偽にする。
2. SignalGetter#getBestNeighborSignal を p で呼ぶ。
3. shouldSignal を真に戻す。
4. 2 の値を返す。

SignalGetter#getBestNeighborSignal の手順。

1. 下・上・北・南・西・東の順に、隣のブロックへ SignalGetter#getSignal を問う (方向は p から隣へ向かう方向)。
2. 15 以上が出たら、その場で 15 を返す。
3. 最後まで行けば最大値を返す。

SignalGetter#getSignal は、隣が導体なら「隣自身の getSignal」と「隣への強い信号の最大 (getDirectSignalTo)」の大きい方を返す。導体でなければ隣自身の getSignal を返す。
この間、ダストの getSignal と getDirectSignal は 0 なので、次のものは値に入らない。

- 隣のダスト自身
- ダストだけが充電している導体

入るものは、信号源 (レバー・トーチ・リピーターの出力面・レッドストーンブロックなど) と、信号源が強く充電している導体。
ターゲットのように「導体であり信号源でもある」ブロックは、自身の出力と強い充電の大きい方になる。

### 4.10 隣のダストから読む値 (RedstoneWireEvaluator#getIncomingWireSignal)

1. 最大値 m を 0 にする。
2. 北・東・南・西の順に、横 n = p + d について次をする。
   1. n がダストなら、その power で m を更新する。
   2. n が導体で、かつ p の真上が導体でないなら、n の真上がダストのとき、その power で m を更新する (上りを読む)。
   3. 2 に当たらず、n が導体でないなら、n の真下がダストのとき、その power で m を更新する (下りを読む)。
3. m − 1 と 0 の大きい方を返す。

読み方の要点。

- 手順 2.1 は接続の形状を見ない。横がダストなら必ず読む。点のダストも横のダストから読む。
- 上りを読む条件には「n が導体」が入っている。4.2 の形状の条件には入っていない。**ここが形状と電力で違う**。
- だから、ガラス・グロウストーン・上付きハーフなど非導体の段では、上段は下段を読む (2.3) が、下段は上段を読まない (2.2 が不成立)。信号は上りにしか流れない。形状は両方とも接続して見える。
  [実機 1.21.1: wire-step-nonconductor-down] 上から給電すると中段・下段は 0。石の段は 14・13。
- n が導体で p の真上も導体なら、上りも下りも読まない。
  [実機 1.21.1: wire-cut-conductor-power] 真上に slime_block・lodestone・soul_sand・stone を置くと上段は 0 になる。glass では切れない。
- 実験の評価器は、ダストの power を読む所だけを差し替える (計算途中の表に値があればそれを使う)。段の規則は同じ。

### 4.11 近隣更新 (RedstoneWireBlock#neighborChanged)

サーバー側だけで動く。引数は、今の状態・送り主のブロック・Orientation (無いこともある)。

1. 送り主がダストで、かつ実験の評価器を使う世界なら、何もしない (支えの確認もしない)。
2. 支えがあれば (4.5)、電力を更新する (4.12 か 4.13)。Orientation はそのまま渡す。「起点の周りのダストを形状更新するか」は偽。
3. 支えが無ければ、アイテムを落として Level#removeBlock を呼ぶ (フラグ 3)。この中で 4.15 の除去の処理が走る。

既定の評価器の世界では、送り主がダストでも 2 へ進む。ダスト同士の近隣更新で電力が伝わる。

**ダストが出す近隣更新の送り主**。近隣更新が運ぶ「送り主」はブロックの種類だけで、状態も座標も運ばない (→ 04 §4.5・§6.4)。
ダストが自分で配る近隣更新は、**どれも送り主がダスト (redstone_wire)** である。起点がダストでないマス (隣・角の確認の対象の隣・横の導体) でも、送り主は起点のブロックではなくダストである。

| 出す所 | 件数 | 送り主 | 典拠 (26.3) |
|---|---|---|---|
| 既定の評価器の 7 起点 (4.12 の手順 5) | 42 | ダスト | DefaultRedstoneWireEvaluator#updatePowerStrength |
| 設置の上・下 (4.14 の手順 2) | 12 | ダスト | RedstoneWireBlock#onPlace |
| 角の確認 (4.14 の手順 3・4.15 の手順 3) | 対象のダスト 1 本につき 42 | ダスト (配っているダスト。対象のダストと種類は同じ) | RedstoneWireBlock#checkCornerChangeAt |
| 除去の 6 起点 (4.15 の手順 1) | 36 | ダスト (世界の p はもう別のブロックだが、送り主は消えたダスト) | RedstoneWireBlock#affectNeighborsAfterRemoval |
| 右クリックの書き込み (4.16 の手順 5。フラグ 3) | 6 | ダスト (古い状態のブロック。→ 04 §5.4) | Level#setBlock |
| 右クリックの横の導体の周り (4.16 の手順 6) | 向きごとに 5 | ダスト (書いた後の状態のブロック) | RedstoneWireBlock#updatesOnShapeChange |
| 支えを失って消える書き込み (手順 3。フラグ 3) | 6 | ダスト (古い状態のブロック。→ 04 §5.4) | Level#removeBlock → Level#setBlock |

送り主がダストにならないのは、ダストを置く書き込み自体の近隣更新だけである。

| 出す所 | 件数 | 送り主 |
|---|---|---|
| 設置の書き込みのフラグ 1 (4.14 の全体の順の 3) | 6 | 古いブロック (置く前に p にあった物。多くは空気) |
| /setblock の後始末 (4.14.1 の手順 3) | 6 | その時点で p にあるブロック (4.14.1 の手順 3) |

- 既定の世界では、上の表のどれも Orientation は無しである (→ 04 §4.9)。
- 実験の評価器の世界では、ダストは送り主がダストの近隣更新を捨てる (手順 1)。上の表の近隣更新は、ダスト以外の受け手にだけ効く。
- 送り主を読む受け手 (ドア・レールほか。→ 04 §5.4) には、これらが「ダストからの更新」として届く。
- 4 つの版 (1.21.1・26.2・26.3・26.4-pre-1) で、送り主は同じである。1.21.1 は送り主の座標も運ぶ (→ 04 §6.4)。

### 4.12 既定の評価器 (DefaultRedstoneWireEvaluator#updatePowerStrength)

入力は p と「渡された状態」。Orientation と真偽の引数は使わない。

1. 目標の値 t を求める。
   1. b = 4.9 の値。
   2. b が 15 なら t = 15。
   3. そうでなければ t = b と 4.10 の値の大きい方。
2. 渡された状態の power が t と同じなら、何もしないで終わる。
3. 世界の p にある今の状態が、渡された状態とまったく同じ (全プロパティが同じ) なら、power を t にした状態をフラグ 2 で書く。
   - この書き込みは近隣更新を出さない。
   - 形状更新は出す (4.7 の 1〜3)。隣のオブザーバーはここで変化を検知する。
4. 空の HashSet を作り、p を入れ、続けて p の下・上・北・南・西・東を入れる。
5. HashSet の反復順に、各位置 q について Level#updateNeighborsAt を呼ぶ。送り主はダスト。
   - 1 回の呼び出しは、q の西・東・下・上・北・南へ近隣更新を出す。除外する方向は無い。
   - 合計 7 起点 × 6 方向 = 42 件。

手順 3 が偽でも、手順 4 と 5 は実行される。偽になるのは次のとき。

- 除去の処理から呼ばれたとき (渡された状態は消えたダストの状態。世界には別のブロックがある)。
- 近隣更新が状態を抱えたまま届き、その間に p の状態が変わったとき (CollectingNeighborUpdater の「状態つきの更新」。→ 04_set-block-and-updates.md)。

#### 4.12.1 42 件の届き先

| 届き先 | 回数 | 内訳 |
|---|---|---|
| p 自身 | 6 回 | 隣 6 マスを起点とする更新が、それぞれ p へ戻ってくる |
| p の隣 6 マス | 各 1 回 | 起点 p から |
| p から 2 マス離れた直線上の 6 マス | 各 1 回 | 隣の起点から |
| p の斜め (辺を共有する 12 マス) | 各 2 回 | 2 つの隣の起点から |

p 自身は 6 回、近隣更新を受ける。そのたびに 4.11 → 4.12 が走る。値が変わらなければ手順 2 で終わる。

#### 4.12.2 HashSet の反復順

HashSet は Java 標準のもの (初期の入れ物 16 個。7 要素では広がらない)。
反復は入れ物の番号の昇順。同じ入れ物の中は挿入順 (→ 18_determinism-java-semantics.md と同じ規則)。

位置のハッシュ値 h は「(y + z × 31) × 31 + x」を 32 ビットの符号つき整数で計算したもの [26.3 読解: Vec3i#hashCode]。
入れ物の番号は「h と、h を符号なしで 16 ビット右へずらした値との排他的論理和」の下位 4 ビット。

7 要素のハッシュ値は、p の値を h0 として次のとおり。

| 要素 | 挿入順 | ハッシュ値 | 16 で割った余りの差 |
|---|---|---|---|
| p | 1 | h0 | 0 |
| 下 | 2 | h0 − 31 | +1 |
| 上 | 3 | h0 + 31 | −1 |
| 北 | 4 | h0 − 961 | −1 |
| 南 | 5 | h0 + 961 | +1 |
| 西 | 6 | h0 − 1 | −1 |
| 東 | 7 | h0 + 1 | +1 |

31 は 16 で割ると 15 余り、961 は 1 余る。だから 7 要素は通常、3 つの組に分かれる。

| 組 | 要素 (組の中の順は固定) |
|---|---|
| 組 A | 上・北・西 |
| 組 B | p |
| 組 C | 下・南・東 |

3 つの組がどの順に並ぶかは座標で決まる。無作為な座標で数えると、次の 6 通りでほぼ全部になる (下の割合は x・z が ±2000、y が −64〜316 の範囲で 20 万点を数えた概算)。

| 順 | 割合 |
|---|---|
| A → B → C (上・北・西・p・下・南・東) | 約 24% |
| C → B → A (下・南・東・p・上・北・西) | 約 24% |
| B → A → C | 約 12% |
| A → C → B | 約 12% |
| B → C → A | 約 12% |
| C → A → B | 約 12% |

例外がある。7 つのハッシュ値が 65536 の倍数 (0 を含む) をまたぐと、上位ビットとの排他的論理和が要素ごとに変わり、組が崩れる。
同じ 20 万点で数えると、上の 6 通りに入らないものは約 3% (順は 50 通りほどに散る)。北と南のハッシュ値が h0 から 961 離れているので、またぐ割合はおよそ 961 × 2 ÷ 65536 になる。
**原点の近くはこの例外に当たる**。実機 fixture は原点の近くに置くことが多いので、規則ではなく計算で求めること。

| p (x, y, z) | h0 | 反復順 |
|---|---|---|
| (0, 1, 0) | 31 | 下・南・東・北・上・西・p |
| (1, 1, 0) | 32 | p・北・下・南・東・上・西 |
| (2, 1, 0) | 33 | 上・西・p・下・南・東・北 |
| (0, 0, 0) | 0 | p・北・西・南・東・下・上 |
| (5, 64, 5) | 6794 | 上・北・西・p・下・南・東 |
| (−3, 64, −7) | −4746 | 下・南・東・p・上・北・西 |
| (100, 70, 200) | 194470 | p・下・南・東・上・北・西 |

この表は、上の規則を小さなスクリプトで計算したもの [26.3 読解 + 計算]。実機での裏づけは §8 のプローブ P1 で取る [要実機]。
`packages/sim/src/updates.ts` の javaHashSetOrder は同じ規則を実装している。

#### 4.12.3 連鎖の形

近隣更新は CollectingNeighborUpdater が配る。動きは次のとおり (詳しくは → 04_set-block-and-updates.md)。

- 処理中に出た更新は、出た順に「今の更新のすぐ後」へ積まれる。つまり深さ優先。
- 6 方向へ配る更新は、1 方向を済ませるたびに、そこで出た更新を先に全部片づけてから次の方向へ進む。
- 手順 3 の形状更新は、手順 5 の近隣更新より先に出ているので、先に処理される。

例。レバーの横に A・B・C の順でダストが並ぶ。レバーを入れる。

1. A が近隣更新を受ける。目標は 15。A = 15 を書く。形状更新と 7 起点を積む。
2. 積んだ順に処理が進む。どれかの起点から B へ近隣更新が届く。
3. B の目標は 14。B = 14 を書く。B の 7 起点は、A の残りの起点より先に処理される。
4. C も同じ。C = 13。
5. 連鎖が戻ってきて、A の残りの起点が処理される。値は変わらないので何も起きない。

レバーを切るとき。

1. A の目標は、B (14) − 1 = 13。A = 13 を書く。
2. B が更新を受ける。目標は、A (13) と C (13) の大きい方 − 1 = 12。B = 12。
3. 次に更新を受けたダストが、隣の値 − 1 へ下がる。これを繰り返して 0 まで下がる。
4. **途中の値がそのつど世界に書かれる**。書くたびに形状更新と 42 件の近隣更新が出る。

最終の値は、信号源からの距離で決まる値と一致する。途中の順と回数は、HashSet の反復順と送信順で決まる。
すべて同じ tick の中で終わる [実機 1.21.1: instant-wire]。

途中の値が見える相手。

| 相手 | 見え方 |
|---|---|
| オブザーバー | 書き込みのたびに形状更新を受ける。最初の 1 回で予約するので、回数は効きにくい |
| リピーター・コンパレーター・トーチ | 近隣更新を受けた時点の値で予約を判断する。実行時にもう一度読む |
| ピストン・ドロッパーなど | 近隣更新を受けた時点の値で動く。**最初に届いた順がブロックイベントの順になる** |

[実機 1.21.1: two-piston-locational] 対称に置いた 2 個のピストンの順は、近隣更新の届く順で決まる。

### 4.13 実験の評価器 (ExperimentalRedstoneWireEvaluator#updatePowerStrength)

入力は、起点の位置・Orientation (無いこともある)・「起点の周りのダストを形状更新するか」。
渡された状態は使わない。評価器は呼び出しごとに新しく作る。

持つもの。

| 名前 | 型 | 中身 |
|---|---|---|
| 下げる待ち行列 | 先入れ先出し | 値が下がるかもしれないダストの位置 |
| 上げる待ち行列 | 先入れ先出し | 値が上がるかもしれないダストの位置 |
| 表 | 挿入順を保つ写像 | 位置 → 「Orientation の番号 × 16 + power」 |

表の値の作り方。初めて登録する位置は、渡された Orientation と power を入れる。**すでにある位置は Orientation を変えず、power だけを入れ替える**。
ダストの power を読むときは、表にあれば表の値を使う。無ければ世界の値を使う。

#### 4.13.1 最初の Orientation

1. Orientation が渡されていればそれを使う。無ければ世界の乱数から 48 通りの 1 つを引く。
2. 上を「上 (UP)」に直す。
3. 横の偏りを「左」に直す。

#### 4.13.2 値を決める

1. 起点がダストなら、表に「起点 → 今の power・最初の Orientation」を入れ、下げる待ち行列へ入れる。
2. 起点がダストでなければ (除去のとき)、起点から 4.13.3 の「広げる」を呼ぶ。渡す値は power 0・最初の Orientation・「下げてよい」は真。
3. 下げる待ち行列が空になるまで、先頭を取り出して次をする。
   1. 表から、その位置の古い値と Orientation を読む。
   2. b = 周りのブロックからの値 (4.9)。w = 隣のダストからの値 (4.10。表を優先して読む)。新しい値 = b と w の大きい方。
   3. 新しい値が古い値より小さければ、書く値は 0。さらに b が 0 より大きく、上げる待ち行列に無ければ、上げる待ち行列へ入れる。
   4. そうでなければ、書く値は新しい値。
   5. 書く値が古い値と違えば、表の power を入れ替える。
   6. その位置から「広げる」を呼ぶ。渡す値は書く値・その位置の Orientation・「下げてよい」は「古い値が新しい値より大きい」。
4. 上げる待ち行列が空になるまで、先頭を取り出して次をする。
   1. 表から古い値と Orientation を読む。b と w を求める。新しい値 = 大きい方。
   2. 新しい値が古い値より大きければ、表の power を入れ替える。
   3. 新しい値が古い値より小さければ、例外を投げる (起きないはずの状態)。
   4. その位置から「広げる」を呼ぶ。渡す値は新しい値・Orientation・「下げてよい」は偽。

下げる段では、値が下がるダストをいったん 0 にする。信号源に直接つながるものだけを上げる待ち行列へ回す。
上げる段で、残っている値から正しい値を広げ直す。

#### 4.13.3 広げる (ExperimentalRedstoneWireEvaluator#propagateChangeToNeighbors)

入力は、位置 q・値 v・Orientation o・「下げてよい」。

1. o の水平の 4 方向 (後ろ・前・横・横の逆) の順に、q の横のマスを 4.13.4 で調べる。渡す Orientation は「o の前をその方向に変えたもの」。
2. o の垂直の 2 方向 (下・上) の順に、次をする。
   1. その方向の q の隣 (真下または真上) が導体かを調べる。
   2. o の水平の 4 方向の順に、次をする。
      - 垂直が上で、q の真上が導体でないなら、横の 1 段上のマスを 4.13.4 で調べる。
      - 垂直が下で、q の横のマスが導体でないなら、横の 1 段下のマスを 4.13.4 で調べる。

上りを調べる条件には「横が導体」が入っていない (4.10 とは違う)。調べられた側は自分の規則 (4.10) で読むので、結果は変わらない。待ち行列に入る範囲が少し広いだけ。

#### 4.13.4 隣のダストを待ち行列へ入れる (ExperimentalRedstoneWireEvaluator#enqueueNeighborWire)

入力は、位置 r・送り元の値 v・Orientation・「下げてよい」。r がダストでなければ何もしない。

1. r の今の値 c を読む (表を優先)。
2. c が v − 1 より小さく、上げる待ち行列に無ければ、上げる待ち行列へ入れ、表へ「r → c・Orientation」を登録する。
3. 「下げてよい」が真で、c が v より大きく、下げる待ち行列に無ければ、下げる待ち行列へ入れ、表へ同じく登録する。

#### 4.13.5 世界へ書く

表の登録順に、各位置について次をする。

1. その位置が今もダストで、power が表の値と違えば、書く。
   - フラグは 2 + 128。
   - ただし「起点の周りのダストを形状更新するか」が真で、表の最初の要素のときだけ、フラグは 2。
2. そうでなければ、その位置を表から外す。

フラグ 128 つきの書き込みは、形状更新の受け手がダストのとき、その形状更新を捨てる [26.3 読解: NeighborUpdater#executeShapeUpdate]。
ダスト以外 (オブザーバーなど) には届く。斜めの通知 (4.7) の受け手はダストなので、すべて捨てられる。
「形状更新するか」が真になるのは設置のときだけ (4.14)。

#### 4.13.6 近隣更新を出す (ExperimentalRedstoneWireEvaluator#causeNeighborUpdates)

表に残った位置を登録順に回る。各位置 q について次をする。

1. 表から Orientation o を読む。世界から q の今の状態を読む。
2. o の 6 方向 (後ろ・前・横・横の逆・下・上) の順に、次をする。
   1. その方向が「接続している」かを見る。水平は **保持値のプロパティ** で決める。下は常に真。上は常に偽。
   2. 接続していなければ飛ばす。
   3. その方向の隣 n へ近隣更新を出す。送り主はダスト。Orientation は「o の前をその方向に変えたもの。ただし上下方向なら o のまま」。状態は今読んだ n の状態を抱えて渡す。
   4. n が導体なら、3 の Orientation の 6 方向の順に、n の隣へ近隣更新を出す。q へ戻る方向だけは除く。Orientation は同じ規則で前を変える。

結果として、近隣更新が届くのは次の範囲だけ。

- 接続している水平方向の隣と、真下。
- それが導体なら、その先の 5 マス。

真上と、接続していない水平方向には届かない。既定の評価器の 42 件よりずっと少ない。
受け手がダストなら、4.11 の手順 1 で無視される。

手順 2.1 は保持値を使う (4.8 のような計算し直しをしない)。保持値が実情とずれていると、届く範囲もずれる。

#### 4.13.7 Orientation の要点

| 項目 | 内容 |
|---|---|
| 構成 | 上 (6 方向)・前 (上と直交する 4 方向)・横の偏り (左 / 右) |
| 総数 | 6 × 4 × 2 = 48 |
| 横 | 「前 × 上」の外積の方向が右。偏りが右ならその方向、左ならその逆 |
| 6 方向の並び | 後ろ・前・横・横の逆・下 (上の逆)・上 |
| 水平の並び | 上の並びから、上の軸でないものを順に取る (4 個) |
| 垂直の並び | 上の並びから、上の軸のものを順に取る (下・上) |
| 番号 | (上の序数 × 4 + 前の鍵) × 2 + 偏りの序数。前の鍵は「軸の区別 × 2 + 正負」。軸の区別は、上が Y 軸なら「前が X 軸で 1・Z 軸で 0」、上が Y 軸でなければ「前が Y 軸で 1・それ以外で 0」。正負は正の向きが 0・負の向きが 1。偏りの序数は左が 0・右が 1 |
| 前を変える | 新しい前が今の上と同じなら、上は「今の前の逆」になる。今の上の逆なら、上は「今の前」になる。それ以外は上を保つ |
| 上を変える | 新しい上が今の前と同じなら、前は「今の上の逆」になる。今の前の逆なら、前は「今の上」になる。それ以外は前を保つ |
| 乱数 | 世界の乱数から 0〜47 を 1 つ引く |

例。上が UP・前が北・偏りが左なら、横は西。6 方向は 南・北・西・東・下・上。

実験の評価器では、上は常に UP・偏りは常に左になる。前は「信号が来た向きの先」。だから各ダストは、来た側 → 先 → 左 → 右 → 下 の順に更新を出す。
真上や真下から更新が来たときは、前が上下を向いた Orientation が渡される。上を UP に直すと、前は次のように置き換わる [26.3 読解: Orientation の生成 (上を変える表)]。

| 渡された Orientation の前 | 上を UP に直した後の前 |
|---|---|
| 上 (UP) | 渡された Orientation の「上」の逆 |
| 下 (DOWN) | 渡された Orientation の「上」 |
| 水平 | そのまま |

渡された Orientation の「上」は、6 方向へ配る更新が最初に乱数で引いた Orientation から決まる水平の向き (引いた Orientation の上が水平ならそのまま。垂直なら、引いた Orientation の前かその逆)。だから **水平の向きが乱数になる**。
実験の評価器が自分で出す近隣更新は、上下方向では Orientation を変えずに渡す (4.13.6 の手順 2.3) ので、ここには当たらない。
Orientation が渡されない呼び出し (設置・除去) では、評価器が自分で乱数を 1 回引く [26.3 読解: ExperimentalRedstoneWireEvaluator#getInitialOrientation]。
既定の世界では Orientation は常に無い。乱数も引かない [26.3 読解: ExperimentalRedstoneUtils#initialOrientation]。

### 4.14 設置 (RedstoneWireBlock#onPlace)

呼ばれる契機は、LevelChunk#setBlockState が新しい状態を入れた直後。フラグ 512 があれば呼ばれない。
古い状態が同じブロック (ダスト) のとき、またはクライアント側のときは何もしない。power や形状の書き込みではここを素通りする。

1. 電力を更新する (4.12 か 4.13)。Orientation は無し。「起点の周りのダストを形状更新するか」は真。
2. p の上、p の下の順に、Level#updateNeighborsAt を呼ぶ (それぞれ 6 件)。送り主はダスト。
3. 隣のダストの周りを更新する (RedstoneWireBlock#updateNeighborsOfNeighboringWires)。
   1. 北・東・南・西の順に、p の横のマスで「角の確認」をする。
   2. 北・東・南・西の順に、横のマスが導体ならその真上で、導体でなければその真下で「角の確認」をする。

「角の確認」(RedstoneWireBlock#checkCornerChangeAt)。対象のマスがダストでなければ何もしない。ダストなら次をする。

1. 対象のマスを起点に Level#updateNeighborsAt を呼ぶ。
2. 下・上・北・南・西・東の順に、対象の隣を起点に Level#updateNeighborsAt を呼ぶ。

送り主は 1 も 2 もダストである (配っている側のダスト。4.11 の表)。

つまり隣のダスト 1 本につき 7 起点 × 6 = 42 件。順は HashSet ではなく、宣言順で固定。
これは「ダストを置くと隣のダストの形状が変わり、給電先が変わる」ことへの手当て。隣のダストの周りのブロックが読み直す。

設置の全体の順 (プレイヤーがアイテムで置く場合。フラグは 11。書き込みの前後の手順は → 04 §4.13)。

1. LevelChunk#setBlockState が状態を入れる。
2. onPlace が走る (上の 1〜3)。
3. Level#setBlock へ戻る。p の今の状態が「入れようとした状態」と同じなら、フラグ 1 の近隣更新 (6 件。送り主は古いブロック) と形状更新 (4.7) を出す。

**落とし穴**。手順 2 で power が変わると、p の状態は「入れようとした状態」と違うものになる。すると手順 3 の近隣更新と形状更新は **出ない** [26.3 読解: Level#setBlock は書き込み後の状態が同じときだけ後処理をする]。
このとき代わりに届いているものは、power の書き込みが出した形状更新 (新しい power の状態から) と、評価器の 42 件。
置いた瞬間に給電されるダストと、されないダストで、周りへ届く更新の種類と順が違う。観測できる差が出るかは [要実機] (§8 P4)。

#### 4.14.1 /setblock で置く場合

実機 fixture は /setblock でダストを置くことが多い。プレイヤーの設置とは 3 点で違う [26.3 読解: SetBlockCommand・BlockInput#place・Block#updateFromNeighbourShapes・ServerLevel#updateNeighboursOnBlockSet]。

1. 書く前に、指定された状態を周りに合わせて直す (strict でないとき)。
   1. 西・東・北・南・下・上の順に、その方向の隣を相手として RedstoneWireBlock#updateShape を掛ける (世界にはまだ書かない)。
   2. 下の段で空気が返る (支えが無い) と、そこから先は空気として進み、最後に「結果が空気なら、指定された状態に戻す」で元へ戻る。つまり **支えが無くても置ける**。次に近隣更新を受けたときに 4.11 の手順 3 で消える。
   3. コマンドに明記したプロパティは、直した後の状態へ上書きする。明記しなかったプロパティだけが周りに合う。
2. 書き込みのフラグは 2 + 256。フラグ 1 が無いので、Level#setBlock の 6 件の近隣更新は出ない。onPlace は走る (4.14 の 1〜3)。形状更新は「状態が同じなら」出る (4.14 の落とし穴は同じ)。
3. 書いた後に ServerLevel#updateNeighboursOnBlockSet が走る。古いブロックの除去の処理 (空気なら何もしない) → p の隣 6 マスへの近隣更新 (送り主は **その時点で p にあるブロック** = ダスト)。この 6 件は、onPlace で power が変わっていても必ず出る。

結果。

| 指定 | 周り | 置かれる状態 |
|---|---|---|
| プロパティ無し (4 方向 none = 点) | 生の接続 0 本 | 点のまま (最後の「上」の段で点の保持が効く) |
| プロパティ無し | 生の接続 1 本以上 | 4.3 の結果 (1 本なら直線) |
| 4 方向を明記 | 何でも | 明記したとおり (実情とずれた保持値を作れる。5.2) |
| 一部だけ明記 (例: 北だけ side) | 生の接続 0 本 | 十字 (北の指定で点でなくなり、直す段で十字になる。明記した北は side のまま。明記しなかった 3 方向は直した結果の side) |

strict のとき (フラグ 2 + 816) は、状態を直さず、onPlace も形状更新も後処理も無い。指定した状態がそのまま入り、power も計算されない。
[版差 1.21.1] 1.21.1 の /setblock はフラグ 2 で、後処理は 6 件の近隣更新だけ (送り主はコマンドで指定したブロック)。strict は無い。
書く前に状態を直す所は同じだが、**明記したプロパティを上書きし直す段 (手順 1.3) が 1.21.1 には無い**。1.21.1 では 4 方向を明記しても周りに合わせて直される (例: 孤立した位置に「北は side・東南西は none」と 4 方向を明記しても十字になる)。26.2 以降は明記したとおりに入る [26.3 読解: BlockInput#overwriteWithDefinedProperties。1.21.1 の BlockInput#place には無い]。
今の実機ハーネス (1.21.1) の fixture でダストの形を明記しているものは、26.3 で撮り直すと保持値が変わりうる。→ 19_version-diffs.md

### 4.15 除去 (RedstoneWireBlock#affectNeighborsAfterRemoval)

呼ばれる契機は、LevelChunk#setBlockState がブロックの種類を変えたとき。ただし書き込みにフラグ 1 かフラグ 64 が要る。
呼ばれる時点で、世界の p にはもう新しいブロック (多くは空気) が入っている。新しいブロックの onPlace より前。

ピストンで動かされたときは何もしない。それ以外は次の順。

1. 下・上・北・南・西・東の順に、p の隣を起点に Level#updateNeighborsAt を呼ぶ (6 起点 × 6 = 36 件)。送り主はダスト (消えたダスト。世界の p にある新しいブロックではない)。
2. 電力を更新する (4.12 か 4.13)。渡す状態は消えたダストの状態。Orientation は無し。「形状更新するか」は偽。
3. 隣のダストの周りを更新する (4.14 の手順 3 と同じ)。

手順 2 の中身 (既定の評価器)。

- p にダストがあるものとして目標を計算する。
- 消えたダストの power と同じなら何もしない。
- 違えば、書き込みはせず (世界の状態が違うので)、7 起点 × 6 の近隣更新だけを出す。
- 例: 14 と 12 のダストに挟まれた 13 のダストを消すと、目標は 13 のまま。追加の更新は出ない。隣のダストは手順 1 の更新で計算し直す。

手順 2 の中身 (実験の評価器)。

- p はダストでないので、p から power 0 で「広げる」。値を持つ隣のダストがすべて下げる待ち行列へ入る。

フラグ 1 も 64 も無い書き込みでダストが消えると、このフックは呼ばれない。そのときの扱いは呼び出し側による。

| 消し方 | フック |
|---|---|
| プレイヤーが壊す・支えを失う (フラグ 3) | LevelChunk#setBlockState から呼ばれる |
| ピストンが壊す (フラグ 18) | 書き込みでは呼ばれない。ピストンが後から自分で呼ぶ (下の注。→ 13_pistons.md) |
| /setblock (フラグ 2 + 256) | 書き込みでは呼ばれない。コマンドが後から ServerLevel#updateNeighboursOnBlockSet の中で呼ぶ。新しいブロックの onPlace と形状更新より後になる (→ 04_set-block-and-updates.md) |
| /setblock の strict (フラグ 2 + 816) | 呼ばれない |

注。ピストンがダストを壊すときの順 [26.3 読解: PistonBaseBlock#moveBlocks]。

1. アイテムを落とし、フラグ 18 (2 + 16) で空気を書く。フラグ 16 があるので、この書き込みは形状更新を出さない。フラグ 1 も 64 も無いので、除去の処理も走らない。
2. 動かすブロックを moving_piston へ書き換える処理が全部済んだ後で、壊したブロックごとに次を順に行う。
   1. 除去の処理 (4.15 の 1〜3。「ピストンで動かされた」は偽で呼ぶ)。
   2. 壊したダストの古い状態で、斜めの通知 (4.7) をフラグ 2 で出す。
   3. 壊した位置の隣 6 マスへ近隣更新を出す (送り主はダスト)。
3. 隣のダストが受ける水平の形状更新は、壊した位置へ入ってくる moving_piston の書き込みから届く (1 の書き込みからは届かない)。

除去の処理が走る時点で、壊した位置にはもう moving_piston が入っていることが多い。手順 2 の「p にダストがあるものとして目標を計算する」は、その世界で行われる。細部と順は → 13_pistons.md。
[実機 1.21.1: destroy-push-dust] 押された石がダストを壊し、隣のダストの形が変わる。

### 4.16 右クリック (RedstoneWireBlock#useWithoutItem)

1. プレイヤーに建築の権限が無ければ、何もしない (PASS)。
2. 今の状態が十字でも点でもなければ、何もしない (PASS)。
3. 十字なら「4 方向 none」、点なら「十字の基準状態」を候補にする。power は今のまま入れる。
4. 候補を入力にして 4.3 を呼ぶ。
5. 結果が今の状態と違えば、フラグ 3 で書き、6 へ進んで SUCCESS を返す。同じなら PASS。
6. 北・東・南・西の順に、次をする (RedstoneWireBlock#updatesOnShapeChange)。
   - その方向の「接続しているか」が書く前と後で変わり、かつその方向の横のブロックが導体なら、横のブロックを起点に近隣更新を出す。p へ戻る方向は除く (5 件)。送り主はダスト (起点の導体ではない。4.11 の表)。

読み方の要点。

- 十字 → 点。候補は点。周りに生の接続が 1 本でもあれば、4.3 の結果は点にならない。結果が元の十字と同じなら何も起きない。
  つまり **点にできるのは、生の接続が 0 本のダストだけ**。
  保持値が十字で、生の接続が 1〜3 本 (保持値が実情とずれている) のときは、4.3 の結果 (直線・角・T 字) がフラグ 3 で書かれる。点にはならないが、書き込みと手順 6 は起きる。
- 点 → 十字。候補は十字 (点でない)。生の接続が 0 本なら十字になる。
- 手順 5 の書き込みはフラグ 3 なので、p の隣 6 マスへ近隣更新が届く (送り主はダスト)。横の導体自身はこれで読み直す。
- 手順 6 は、横の導体の「その先」にある装置へ届けるためのもの。
- p 自身の power は変わらない (近隣更新は p へ届かないし、接続の形は power の計算に関係しない)。
- 素手でなくても、持っているアイテムが使われなかったときはここへ来る (→ 09_manual-inputs.md の入力の順)。

### 4.17 評価器を選ぶ条件

世界の有効な機能に redstone_experiments が入っていれば実験の評価器。入っていなければ既定の評価器 [26.3 読解: RedstoneWireBlock#useExperimentalEvaluator]。

- 判定は電力を更新するたびに行う。世界ごとに決まる。
- 機能の旗は 4 つ (vanilla・trade_rebalance・redstone_experiments・minecart_improvements)。既定の旗は vanilla だけ [26.3 読解: FeatureFlags]。
- redstone_experiments は、世界を作るときに実験のデータパックを入れたときだけ有効になる。通常の世界では無効。
- 同じ旗は、近隣更新に Orientation を付けるかどうかも決める (CollectingNeighborUpdater・ExperimentalRedstoneUtils)。

## 5. 端の場合と落とし穴

### 5.1 形状と電力は別の規則

| 場面 | 形状 | 電力 |
|---|---|---|
| 非導体の段 (ガラスなど) の上り | 接続する | 上段は下段を読む |
| 非導体の段の下り | 接続する | 下段は上段を読まない |
| 横がダスト | 接続する | 読む (形状に関係なく) |
| 点のダストの横にダスト | 4.6 の形状更新で接続が立つので、点のまま隣り合うことは通常無い | 読む |
| 下段の真上に導体 | 切れる | 読まない |

### 5.2 保持値と計算し直し

| 使う所 | 見るもの |
|---|---|
| 信号の出力 (4.8) | 計算し直した接続。保持値は点の保持にだけ効く |
| 形状更新 (4.6) | 保持値と生の接続を比べる |
| 斜めの通知 (4.7) | 保持値 |
| 実験の評価器の近隣更新 (4.13.6) | 保持値 |
| 描画・当たりの形 | 保持値 |
| 右クリック (4.16) | 保持値が十字か点か |

構造物の配置や、4 方向を明記した /setblock (26.2 以降。4.14.1) で「延長されていない」保持値 (例: 北だけ side) を置くと、形状更新が来るまでそのまま残る。信号の出力は十字として答える。
プロパティを明記しない /setblock は、書く前に周りへ合わせて直すので、ずれた保持値にはならない (4.14.1)。
形状更新が来ても、直るのは届いた方向に関わる所だけ (4.6 の手順 2)。全部が直るのは、真上から届いたとき・保持値が十字のとき・届いた方向の接続の有無が変わったとき。

### 5.3 給電先へ通知が届かない場合

形状が変わって給電先が変わっても、近隣更新が出るのは次のときだけ。

- ダストの設置と除去 (隣のダストの周り 42 件)。
- 右クリック (横の導体の先 5 件と、フラグ 3 の 6 件)。

それ以外 (接続先のブロックが横に現れる・消える) では、給電を失った側にも得た側にも通知が無い。
その変化を起こした書き込みがフラグ 1 を持てば、書かれたマスの隣 6 マスには近隣更新が届く。そこに入らないマス (ダストを挟んで反対側など) は古いまま残る。
[実機 1.21.1: dust-reshape-stale-target]

### 5.4 ダストを読む側の特別扱い

- リピーターとコンパレーターの背面は、相手がダストなら power を直接読む。ダストがそちらを向いているかは見ない [26.3 読解: DiodeBlock#getInputSignal]。→ 07_diodes.md
- コンパレーターの側面も、相手がダストなら power を直接読む [26.3 読解: SignalGetter#getControlInputSignal]。→ 07_diodes.md

### 5.5 shouldSignal は全世界で 1 個

RedstoneWireBlock のインスタンスが持つ。次元ごとではない。1 スレッドで順に処理する限り問題は無い。
Rust では「ダストを信号に数えない」という引数か、問い合わせの種類として持てばよい。

### 5.6 よくある誤解

| 誤解 | 実際 |
|---|---|
| ダストは弱い信号しか出さない | 強い信号として出している。他のダストが読むときだけ隠す |
| 孤立したダストは点 | 十字。点は右クリックか、点として置かれたときだけ |
| 形状が変わると電力を計算し直す | 計算し直さない。近隣更新が来たときだけ |
| HashSet の順は挿入順 (下・上・北・南・西・東) | 座標で変わる。4.12.2 |
| 設置時の隣のダストの更新も HashSet 順 | 宣言順で固定 (4.14) |
| 実験の評価器も 42 件を出す | 接続方向と真下、導体ならその先だけ |
| 除去のフックは必ず呼ばれる | フラグ 1 か 64 が要る。無ければ呼び出し側しだい |

### 5.7 ダストの上のダスト

支えの規則から、ダストの真上や真下にダストは置けない (ダストの上面は頑丈でない)。
4.10 は横がダスト (非導体) のとき、その真下も読む。実在しない配置なので結果には効かない。

### 5.8 挙動に効かないメソッド

| メソッド | 内容 | シミュレーションへの影響 |
|---|---|---|
| RedstoneWireBlock#rotate・#mirror | 構造物の回転と反転で、4 方向のプロパティを入れ替える。power は変えない | 無し (回路ファイルを回して読み込む道具を作るときだけ要る) |
| RedstoneWireBlock#animateTick | power が 0 でなければ粒子を出す。クライアント側だけ | 無し (サーバーの乱数を引かない) |
| RedstoneWireBlock#getShape | 保持値から当たりの形を返す。当たり判定は無い | 無し |
| ExperimentalRedstoneWireEvaluator#causeNeighborUpdates の末尾 | デバッグ表示の購読者がいれば、各ダストの Orientation を送る | 無し |

## 7. Rust で実装するときの要点

### 7.1 状態の持ち方

- ダストの状態は 12 ビットに収まる (接続 2 ビット × 4 + power 4 ビット)。状態表の番号でもよい (→ 05_signals-and-block-properties.md)。
- 「全プロパティが同じ」の比較 (4.12 の手順 3) は、この値の一致で足りる。
- 十字・点の判定は接続 8 ビットのマスクで書ける。

### 7.2 純粋関数に分ける

| 関数 | 入力 | 出力 |
|---|---|---|
| 1 方向の接続 (4.2) | 世界・p・方向・上へ接続できるか | up / side / none |
| 4 方向の接続 (4.3) | 世界・p・今の状態 | 新しい状態 |
| 形状更新 (4.6) | 世界・p・今の状態・方向・運ばれた隣の状態 (下の段だけが使う) | 新しい状態か「消える」 |
| 信号の出力 (4.8) | 世界・p・状態・方向・ダストを数えるか | 0〜15 |
| 周りのブロックの値 (4.9) | 世界・p | 0〜15 |
| 隣のダストの値 (4.10) | 世界・p・power の読み手 | 0〜15 |

4.8 は問い合わせのたびに 4.3 を呼ぶ。4.3 は横 4 マスと、その上下、p の真上を読む (最大 13 マス)。
速さのために保持値で代用してはいけない。保持値と計算し直した値は一致するとは限らない (5.2)。
ただし「保持値が、直前の形状更新の後で正しい」と証明できる範囲では、キャッシュにできる。まず忠実に書き、後で測る。

### 7.3 既定の評価器

- 再帰ではなく、近隣更新のスタック (→ 04_set-block-and-updates.md) の上で動かす。評価器は「書く」「42 件を積む」だけをする。
- 7 起点の順は 4.12.2 の計算で求める。32 ビットの符号つきの掛け算と足し算は wrapping で書く。右へずらすのは符号なし。
- 7 要素を 16 個の入れ物へ入れて番号順に読むだけなので、固定長の配列で書ける。割り当ては要らない。
- 途中の値を省かない。「最終の値を先に求めてから更新を出す」方式は、近隣更新の順と回数が変わるので使わない。
- 42 件のうち p 自身への 6 件も省かない。その時点の世界で計算し直すので、結果が変わることがある。

### 7.4 実験の評価器

- 既定の世界では使わない。まず既定だけを実装し、実験は機能の旗の後ろに置く。
- 表は「挿入順を保つ写像」。Rust では位置 → 添字の写像と、挿入順の配列の組で書く。
- 待ち行列の「入っているか」の確認は線形探索と同じ結果になればよい (集合を併用してよい)。
- Orientation は 48 個の表を起動時に作る。前を変える・上を変える・偏りを変えるは表引き。
- 乱数は世界の乱数を使う。引く回数と順を合わせる必要がある (→ 18_determinism-java-semantics.md)。実験の世界では、近隣更新を出すたびに乱数を引く所がある (ServerLevel#updateNeighborsAt)。

### 7.5 フックの順

- 設置: 状態を入れる → onPlace → (状態が変わっていなければ) フラグ 1 の近隣更新 → 形状更新。4.14 の落とし穴を再現するには、「書き込み後の状態が同じか」の確認を setBlock に入れる。
- 除去: 状態を入れる → (フラグ 1 か 64 があれば) 除去の処理 → 新しいブロックの onPlace → フラグ 1 の近隣更新 → 形状更新。
- どちらも、最上位から呼ばれたときと、近隣更新の処理中に呼ばれたときで、更新の実行の時機が違う (最上位では 1 件ずつその場で最後まで走る。処理中は積まれる)。出る順は同じ。途中で世界を読む判定 (「角の確認」の「ダストか」) だけが、読む時点の違いを受ける。→ 04_set-block-and-updates.md

### 7.6 他のメモとの境界

| 相手 | 境界 |
|---|---|
| 04 | ダストは「どの起点へ・どの順で・どのフラグで」だけを決める。配り方は 04 |
| 05 | 導体か・上面や側面が頑丈か・信号源かは 05 の表を引く |
| 07 | ダイオードがダストの power を直接読む規則は 07 |
| 13 | ピストンがダストを壊すときのフラグと、除去の処理を呼ぶ時機は 13 |
| 18 | HashSet の規則と乱数は 18。このメモの 4.12.2 は 7 要素に絞った結果 |

## 8. 検証用のプローブ回路案

どれも 26.3 の実機で撮る。座標は fixture の原点からの相対。

### P1. 7 起点の順 (HashSet の反復順)

- 目的: 4.12.2 の表を実機で確かめる。
- 配置: ダスト 1 本 (位置 p) を石の上に置く。p の西と東に石を 1 個ずつ。その外側 (p から 2 マス西と 2 マス東) に、上向きのピストンを 1 個ずつ。ダストへの給電は、足元の石を横からリピーターで強く充電する (ダストの横に接続先を置かないので、ダストは十字になり、東西の石を充電する)。
- 変える物: 回路全体を平行移動して、組の順が違う 6 通りの座標と、原点の近くの例外の座標 (0, 1, 0)・(1, 1, 0)・(2, 1, 0) で撮る。
- 観測: ダストが 15 になった tick の、ブロックイベントの順 (どちらのピストンが先か)。
- 期待の要点: 2 マス西のピストンへ届くのは、起点「西」(組 A) からの 1 件だけ。2 マス東は起点「東」(組 C) からの 1 件だけ。だから組 A が組 C より先に来る座標では西が先、逆なら東が先。p の隣に直接置いた装置は起点 p (組 B) からしか届かないので、東西の順は常に西が先になる (比較用に南へ 1 個置くとよい)。座標ごとに期待を計算してから撮る。

### P2. 途中の値と深さ優先

- 目的: 既定の評価器が途中の値を書くこと、順が深さ優先であることを確かめる。
- 配置: ダスト 8 本の直線。片端にレバー。3 本目と 6 本目の横に、ダストを観測面にしたオブザーバーと、その背面にランプ。さらに各ダストの下の石の横にドロッパー (中身は別々のアイテム 1 個)。
- 観測: レバーを切った tick のブロックイベントの順 (ドロッパーの発射順)。オブザーバーの予約 tick。
- 期待の要点: 発射順は、近隣更新が届く順。最終の値を先に決める方式では再現できない。

### P3. 形状の変化で通知が届かない (MC-3703 の 26.3 版)

- 目的: [実機 1.21.1: dust-reshape-stale-target] が 26.3 でも同じかを確かめる。
- 配置: 既存の fixture と同じ。
- 期待の要点: 古い状態のまま残る。26.3 は /setblock の除去の順が違うので、石を置く方の経路で撮る。

### P4. 置いた瞬間に給電されるダスト

- 目的: 4.14 の落とし穴 (後処理が出ない) で観測できる差があるかを確かめる。
- 手段: プレイヤーの設置を撮る入力が要る (→ 04 §8 の「プレイヤーの設置と破壊を撮る手段」)。
- 配置 A: レッドストーンブロックの横の石の上へ、プレイヤーがダストを置く。ダストの上に、下向きのオブザーバー。ダストの横にコンパレーターとピストン。
- 配置 B: 同じ形で、レッドストーンブロックを外したもの (給電されない)。
- 観測: 置いた tick の、予約 tick の登録順とブロックイベントの順。オブザーバーが発火するか。
- 期待の要点: A はフラグ 1 の 6 件が無い。オブザーバーはどちらも発火する (A は power の書き込み、B は設置の書き込みで)。

### P5. 除去の順 (プレイヤー・/setblock・ピストン)

- 目的: 4.15 の 3 つの経路で、周りへ届く順を確かめる。
- 配置: 14・13・12 と並ぶ 3 本のうち、まん中を消す。両隣のダストの下の石の横にピストン。消す位置を観測するオブザーバー。
- 変える物: 消し方 (プレイヤーが壊す・/setblock air・ピストンで壊す・下の石を消して支えを失わせる)。プレイヤーが壊す列は、破壊を撮る入力が要る (→ 04 §8 の「プレイヤーの設置と破壊を撮る手段」。手順は 04 §4.14)。
- 観測: 消した tick のブロックイベントの順と、オブザーバーの予約。
- 期待の要点: プレイヤーと支えの消失は「除去の処理 → 近隣更新 → 形状更新」。/setblock は「形状更新 → 除去の処理 → 近隣更新」。

### P6. 接続の形 (静的)

- 目的: 4.2 の up と side の区別、トラップドア、ホッパーを確かめる。
- 配置: 下段のダストの横に、石・ガラス・上付きハーフ・ホッパー・上付きで閉じたトラップドア・レッドストーンブロック・ターゲットを 1 列ずつ置き、その上にダスト。
- 観測: 落ち着いた後の blockstate。
- 期待の要点: 石・ガラス・レッドストーンブロック・ターゲットは up。上付きハーフ・ホッパー・トラップドアは side。トラップドアを開いた後の状態も撮る [要実機]。

### P7. 右クリック

- 目的: 4.16 の届き先を確かめる。
- 配置: 孤立したダスト (十字) を power 15 にする。足元の石を、横からリピーターで強く充電する (リピーターはダストの斜め下なので、生の接続は立たない)。東に石、その東にピストン。北にランプ。
- 観測: 右クリックした tick と、その後のランプ・ピストンの状態。
- 期待の要点: 点にすると、ランプは 4 tick 後に消え、ピストンは同じ tick に縮み始める。点 → 十字で戻る。ピストンへ届く更新は 4.16 の手順 6 のもの。ランプへ届く更新はフラグ 3 の 6 件のもの。

### P8. 点の保持

- 目的: 点が保たれる条件と、解ける条件を確かめる。
- 配置: 点のダストの横へ、ランプ (接続先でない)・レバー (接続先)・ダストを順に置く。真上へ石を置く。
- 期待の要点: ランプと真上の石では点のまま。レバーとダストでは直線になる。

### P9. 実験の評価器

- 目的: 4.13 の順を確かめる (実験の世界に対応すると決めたときに撮る)。
- 配置: P1 と P2 を、redstone_experiments を有効にした世界で撮る。同じ回路を平行移動しても順が変わらないこと。真上から給電したときに順がばらつくこと。
- 観測: ブロックイベントの順。デバッグ表示の Orientation。

### P10. /setblock で置くダストの形

- 目的: 4.14.1 (書く前に状態を直す・明記したプロパティの上書き) を確かめる。1.21.1 と 26.3 の差も撮る。
- 配置: 石の上の孤立した位置へ、次の 5 通りを /setblock する (足元の石は、横からリピーターで強く充電しておく)。(a) プロパティ無し。(b) 4 方向 side を明記。(c) 「北は side・東南西は none」と 4 方向を明記。(e) 北だけを side と書き、他は書かない。(d) 支えの無い空中へプロパティ無し。別の列で、西にダストがある位置へ (a) と (c)。
- 観測: 置いた直後の blockstate。(c) は北・東・南・西に置いたランプの点き方 (保持値は北だけでも、信号は十字として出るはず)。(d) は隣へ石を /setblock して近隣更新を送り、消えるかどうか。
- 期待の要点: 26.3 は (a) 点・(b) 十字・(c) 北だけ side (信号は十字として出る)・(e) 十字・(d) 置けて、近隣更新で消えてアイテムが落ちる。1.21.1 は (c) が十字になる。[要実機]
