# docs/vanilla — Java 版 26.3 のレッドストーン読解メモ (目次)

Java 版 26.3 のレッドストーンの挙動を、ゲームのコードを読んで日本語でまとめたメモ集である。
Rust (WASM) で同じ挙動のエンジンを組むための土台にする。写経や移植ではない。
このファイルは目次で、読む順・表記・ファイル一覧・更新の手順をまとめる。

---

## 1. 目的

- Java 版 26.3 と**同じ挙動**の Rust (WASM) エンジンを、ブラウザで動かすために作る。その設計の典拠にする。
- ネットの記事だけでは足りない所を、コードの読解で埋める。足りないのは主に次の 4 つである。
  1. tick の中の順 (相の順・予約 tick の並び・更新の配り方)
  2. 書き込みのフラグと、それで出る更新の種類
  3. 乱数をいつ何回引くか、ハッシュ表をどの順に回すか
  4. 版ごとの違い
- 各メモは、条件・定数・フラグ値・優先度・遅延・方向の並びを数値のまま書く。そのまま実装に落とせる粒度を目指した。
- 読んだだけでは決まらない所は [要実機] として残した。正解は実機で撮る。撮り方は docs/research/18_ground-truth-oracle.md、確かめる回路の集め方は docs/research/17_circuit-corpus.md にある。
- このメモ集をもとにした Rust (WASM) エンジンの設計案は docs/research/19_rust-wasm-engine.md にある。各メモの §7 を設計のどこで受けるかの対応表は、その §4.3 にある。

## 8. 書き方の決まり

正は docs/ip-policy.md である。このディレクトリでは次を守った。追記するときも守る。

1. **デコンパイルしたコードの逐語引用はしない**。Java の文・式・シグネチャ・record 宣言を 1 行も写さない。Java のコードフェンスも使わない。
2. メソッドは「ClassName#methodName」と名前だけで書く。引数は日本語で説明する。
3. 典拠は「26.3 クラス名#メソッド名 + 自分の言葉」で書く。条件・定数・フラグ値・優先度・遅延・方向の並びなどの事実は、数値のまま書いてよい (情報を減らさない)。
4. 手順は日本語の番号付きの箇条書きで書く。Java 風の構文にしない。
5. 絶対パスを書かない。リポジトリの中はリポ相対、デコンパイルは「26.3 の ClassName」と書く。
6. 文体は日本語の、だ・である調で、短い文にする。表を使う。英語の識別子 (クラス名・メソッド名・プロパティ名・ブロック ID) は原文のまま書く。

CI の衛生テスト (tools/ip-hygiene.test.ts) が、Java の呼び出し文・修飾子つきのシグネチャ・record 宣言・型つきの引数リスト・Java のコードフェンス・手元の絶対パスの形を落とす。

## 9. 26.4 が出たときの更新手順

既定の方針は「基準は 26.3 のまま、26.4 の差を記録する」である (19 §7 の 7)。基準を上げるかは、手順 8 で別に決める。

1. **デコンパイルする**。tools/decompile/fetch-and-decompile.sh に版 (26.4) を渡す。結果は tools/decompile/out/26.4/ に出る。git の管理外で、コミットしない (tools/decompile/README.md)。
2. **監視クラスの一覧を直す**。tools/decompile/watched-classes.txt の RedStoneWireBlock.java は、26.3 で RedstoneWireBlock.java へ改名された。直さないと --update が止まる (19 §6.5)。足す候補は 19 §9.7 にある (Level・LevelChunk・ServerLevel・SetBlockCommand・BlockInput ほか)。
3. **指紋の基準を 26.3 に移す** (まだなら)。tools/decompile/spec-drift.sh を --update 26.3 で実行し、fingerprints.json を 26.3 にする。今の基準は 26.2 なので、移さないと 26.4 との比較に 26.2 → 26.3 の差が混ざる。
4. **比べる**。spec-drift.sh を --check 26.4 で実行し、DRIFT の行のクラスを読む。CI (.github/workflows/spec-drift.yml) は週次で最新の release と比べ、差があれば issue を起票する。
