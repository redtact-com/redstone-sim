# 19. Rust (WASM) エンジンの設計

Java 版 26.3 と同じ挙動のエンジンを Rust で書き、WASM でブラウザに載せる。その設計を決める。
この文書は #432 の PR で方針レビューにかける。承認の後に実装の issue を立てる。各 issue も draft PR で方針を確かめてから実装する。

- 作成日: 2026-11-26。コードは 1 行も書いていない。
- 目標 (ユーザの原文): 「実際のゲーム(java)と全く同じ挙動にしたいので　ゲームのコードから解析とまではいかないけど　細かくメモをとって　ないようを把握し rust(たぶんweb上で一番軽く動かせる？)で組めるようにしたい」
- 基準の版は 26.3 である。
- 参照の書き方:
  - **V06 §7.3** は docs/vanilla の 06 番のメモの §7.3 を指す
  - **R18 §4.2** は docs/research の 18 番の資料の §4.2 を指す
  - **V18 の R4** は docs/vanilla 18 §2.3 の表 (順が結果を変える箇所) の R4 の行を指す。docs/research の番号 (R13 など) と紛れないよう、本文でも「V18 の」を付ける
  - **報告** は 2026-11-26 の速度比較 (#432 の作業。今の TS エンジンと Rust 製の mc-tick を比べた。リポジトリの外にある)
- 確かさの表記:
  - **[実測]** 報告か、案を作るときの追加の計測で測った
  - **[推定]** 見込み。マイルストーンの中で実測に置き換える
  - **[要実機]** 26.3 を動かして確かめる必要がある
- 設計は 3 つの案を作り、2 つの観点 (正確さ・工学) で採点してまとめた (§12)。

## 0. 結論

### 0.1 何を作るか

1. **26.3 の実行モデルを畳まずに持つ Rust のエンジン**を作る。順序を作る仕組み (相の順・2 層の予約 tick・挿入順のブロックイベント・深さ優先の更新器・Java のハッシュ順・乱数) を、合成も省略もしない。
2. **速くするのは持ち方だけ**にする。世界は u16 の密な配列、性質は前計算の表、キーは整数にする。操作の回数と順は変えない。
3. **今のリポジトリに無理なく入れる**。同じモノレポに crates/ を足す。窓口の型 Engine は @redstone/sim の中に置き、今の SimWorld と同じ形にする。アプリは `?engine=rust` で切り替える。
4. **正解は実機で撮る**。まず 1.21.1 の fixture 150 本を仕分けて使う。26.3 のオラクル (R18 の案 c) の fixture が届いた順に置き換える。
5. **TS エンジンは 1.21.1 互換として凍結して残す**。main の既定は、基準 (§8.3) を満たしてから Rust にする。

### 0.2 なぜ Rust / WASM か

| 観点 | 答え |
|---|---|
| 速さ | wasm は今の TS より 1 tick で 13〜32 倍速い [実測]。同じ作りに書き直した JS と比べても約 2.2 倍速い [実測。合成カーネル] |
| 重さ | ダウンロードは JS の方が軽い (TS 26 KB、Rust は 100〜150 KB の見込み)。遅れて読み込むので、最初の表示は変わらない |
| 正確さ | 64 bit の時刻と予約順、48 bit の乱数、wrapping の 32 bit をそのまま書ける。enum の match は抜けをコンパイルで見つける |
| 検証 | 同じコードを native でも回せる。差分ファジングと CI の適合テストが wasm の 1.75〜2.02 倍速い [実測] |
| どちらにしても書き直し | 今の TS は文字列キーと 1.21.1 寄りの意味論で、26.3 の土台にそのまま使えない |

詳しくは §1 に書く。

## 1. 「Rust は Web で一番軽く動くか」への答え

「軽い」を 4 つに分けて答える。数字は報告の値である (Ryzen 7 5700X・WSL2・Node 22.14)。

### 1.1 速さ: Rust (wasm) が一番軽い

| 回路 (ブロック数) | 今の TS | mc-tick の wasm | mc-tick の native | wasm は TS の何倍速いか |
|---|---:|---:|---:|---:|
| clocks (5,888) | 34.3 ms | 1.07 ms | 0.60 ms | 31.9 |
| dust (4,896) | 4.47 ms | 0.35 ms | 0.17 ms | 12.7 |
| pistons (4,032) | 9.85 ms | 0.42 ms | 0.24 ms | 23.2 |
| mixed (11,540) | 23.3 ms | 1.70 ms | 0.92 ms | 13.7 |

- 値は 1 tick の中央値である。tick 0〜400 の全状態は 3 つの処理系で一致した。同じ仕事をした結果の比較である。
- 20 tps の予算は 1 tick 50 ms である。TS は clocks で 34 ms を使う。60 fps の 1 コマ (16.7 ms) の 2 倍なので、描画と同じスレッドではコマ落ちする。wasm は最大 1.7 ms (p95 3.0 ms) である。
- mixed の 10,000 tick の早送りは、見積もりで TS 約 233 秒、wasm 約 17 秒、native 約 9 秒である。
- wasm は native の 1.75〜2.02 倍の時間がかかる。Rust の速さの約半分が Web に出る。

### 1.2 ダウンロード量: JS が軽い

| もの | brotli | 備考 |
|---|---:|---|
| 今の TS エンジン | 26 KB | esbuild で束ねて minify |
| mc-tick の wasm (opt-level 3 + wasm-opt -O3) | 205 KB | エンティティ・流体・爆発まで含む 35,286 行 |
| 同 (サイズ優先の opt-level z) | 168 KB | tick が 3.9〜4.3 倍遅くなる |
| JS 側の読み込みのコード | 1.2 KB | 測定用ドライバの全体 |
| 参考: アプリ全体の JS | 230 KB | vite build の 1 チャンク [実測。採点のとき再計測で 229,867 B] |
| 参考: テクスチャ | 最大 180 KB | PNG 313 枚。使う分だけ取る |

- エンジン単体では JS が 6〜8 倍軽い。
- この設計の wasm は、目標 100 KB・上限 150 KB (仮) に置く [推定]。範囲が mc-tick より狭いからである。縦切りで測って決め直す (§6)。
- wasm は遅れて読み込む。最初の表示に要る JS (230 KB) は増えない。

### 1.3 起動: 引き分け

| 項目 | TS | wasm |
|---|---:|---:|
| エンジンの読み込み | import 3.0 ms | compile 1.5 ms + instantiate 0.12 ms |
| 初回の組み立て (4 回路) | 42〜103 ms | 40〜80 ms |
| 2 回目以降の組み立て | 25〜65 ms | 15〜39 ms |

V8 は wasm を遅れてコンパイルする。実費は初回の組み立てに混ざる。体感の差は小さい。

### 1.4 メモリ: 引き分け

| 項目 | TS | wasm |
|---|---:|---:|
| 組んだ世界 | 1.06〜3.04 MB | 0.89〜1.91 MB |
| 全体 | (JS のヒープ) | 線形メモリ 2.75〜4.26 MB |

Rust にしても大きくは軽くならない。変化の記録を溜め続ける作りだと、1,500 tick で 13.6〜52.4 MB 溜まった。この設計は記録を tick ごとに空にする (§3.8)。

### 1.5 反対の見方

| 見方 | 根拠 | この設計の受け止め |
|---|---|---|
| JS でも型付き配列と整数キーで書けば近づく | 近隣 6 方向の参照は、文字列キーの Map 95.6 ns、整数キーの Map 10.8 ns、Uint16Array 4.1 ns [実測]。hasScheduledTick だけ索引にした写しで最大 2.33 倍速くなった [実測]。同じ算法と同じ配置の合成カーネルでは、JS 14.5 ns、wasm 6.5 ns、native 4.4 ns だった [実測] | 正しい。今の差 (13〜32 倍) の大半は作りの差である。同じ作りなら差は約 2.2 倍に縮む。ただしエンジン全体では測っていない |
| wasm は native の半分しか出ない | wasm ÷ native が 1.75〜2.02 [実測] | 正しい。それでも JS より速い |
| 比べたのは言語でなく 2 つの実装である | mc-tick は性能を詰めた実装、今の TS は正しさを先に書いた | 正しい。だから持ち方 (§3) を先に決める |
| 同じ範囲の Rust ならもっと小さい | 測っていない | 縦切りと段ごとに測る |
| Web Worker に載せれば TS でも画面は止まらない | — | 正しい。ただし 1 tick の速さは変わらない。早送りの待ち時間はそのまま残る |
| 描画へ渡す費用を測っていない | 報告の wasm は step だけを呼んだ | 重い指摘である。今の描画の作り直しは mixed で 1 回約 26 ms かかる [実測。snapshot 4.2 ms + 構造への変換 21.7 ms]。wasm の 1 tick の約 15 倍である。差分の描画を同じ計画に入れる (§2.6) |
| 測ったのは Node の V8 だけ | ブラウザでは測っていない | Firefox と Safari の比は違いうる。M0-6 で 3 つのブラウザの計測を足す |

### 1.6 それでも Rust にする理由

1. 残る約 2.2 倍は、早送りの待ち時間にそのまま出る。mixed の 10,000 tick は、wasm の 17 秒に対し JS では 37 秒前後になる [推定]。
2. 同じコードを native で回せる。差分ファジングと適合テストに、web と同じ実装を使える。
3. Java の意味論を写しやすい。JS では 64 bit に BigInt か分割が要る。
4. どちらにしても書き直しになる。書き直すなら、言語の差の 2 倍も取る。

引き換えに払うものは 4 つある。ダウンロードの増分 (遅延読み込みで隠す)、CI の Rust のツール、TS の窓口、2 つになるテストの走らせ方である。

### 1.7 まとめ

- tick を速く回す意味では、Rust (wasm) が一番軽い。
- 読み込みの軽さでは、JS が一番軽い。
- 起動とメモリは引き分けである。
- 画面に速さを出すには、エンジンだけでなく描画の差分化が要る。

## 2. 採用した設計の全体

### 2.1 3 つの層

| 層 | 決めること | 土台にした案 |

素子の振る舞いは trait にしない。状態表が持つ `Behavior` (列挙) を match する関数にする。

```rust
pub enum Behavior { Inert, Wire, Repeater, Comparator, Torch, WallTorch, Observer, Lever,
                    Button, Lamp, NoteBlock, Door, Piston, PistonHead, MovingPiston, /* … */ }

pub fn neighbor_changed(lv: &mut Level, pos: Pos, st: StateId, src: BlockId,
                        ori: Option<Orientation>, moved: bool) {
    match lv.table.behavior(st) {
        Behavior::Wire => blocks::wire::neighbor_changed(lv, pos, st, src, ori),
        Behavior::Repeater | Behavior::Comparator => blocks::diode::neighbor_changed(lv, pos, st),
        /* … */
        Behavior::Inert => {}
    }
}
```

理由は 4 つある。

1. 素子は `&mut Level` の全体を取り、再入する。関数なら借用がぶつからない。
2. 間接呼び出しが無く、wasm が小さく速い。
3. match の網羅性で、フックの抜けをコンパイルが見つける。
4. 「撤去フックを呼ぶ条件」などの共通の処理を set_block の 1 か所に置ける。

素子は独自の順序の規則を持たない。順序は骨格の部品が決める。素子は「何を・どの順で頼むか」だけを書く (V11 §7 の 11)。

### 2.5 JS との境界

| 項目 | 決め方 |
|---|---|
| 書き出し | 素の C ABI。wasm-bindgen を使わない。import は 0 個で、Node・ブラウザ・Worker で同じに動く |
| 世界 | ハンドル (番号) で作る。wasm のインスタンスは 1 つで、世界は複数持てる。チェックポイント・並走の差分・LivePage で同時に要る |
| 状態 | StateId (u16) で渡す。文字列が境界を越えるのは、読み込みのパレットの解決だけである |
| 変化 | tick の後に、正味で変わった (x, y, z, StateId) の列を線形メモリに書く。JS は型付き配列の窓で読む。写しは作らない |
| BE の変化 | 同じ形の別の列で渡す (位置・種類・値) |
| 入力 | 1 操作 1 関数。use・setblock (strict あり)・place (プレイヤーの設置)・break (プレイヤーの破壊)・item・container・lectern・occupancy。区間の印 (§4.1) を引数で受ける |
| 観測 | 音・GameEvent・出したエンティティ・trace は、有効にしたときだけリングバッファへ書く |
| エラー | 状態コード (ビットの集合) で返す。文は JS 側の表で引く。黙って捨てない |
| 保存と復元 | 不透明なバイト列。状態表のハッシュを先頭に持つ |

この設計を実装する repo (redtact-com/redstone-engine) は、次の 3 点でこの節と違う形にすると決めた (#13)。作るのは redstone-engine の PR #16 で、この記録を書いた時点では draft である (develop の窓口は版 1 のまま)。窓口の正は、その repo の docs/wasm-abi.md である。

| 所 | この節の元の形 | redstone-engine の形 | 理由 |
|---|---|---|---|
| 入力の一覧 | use・setblock・place・item・container・lectern・occupancy。壊す入力が無かった | 「プレイヤーが壊す」(break) を足す。区間 A (§4.1)。手順は V04 §4.14 | アプリの消しゴムと、置き換え (壊す → 置く) に要る。編集の間もエンジンの世界に置く・壊すを入れる形にする (§6.3 の記録) |

- Engine の口は、アプリ・エディタ・道具・下流が SimWorld に呼んでいるメソッドの和集合である。M0-4 で呼び出し元を数え直して確定する。
- **SimWorld はそのまま Engine を満たす**。足すのは engineKind・rulesVersion・dispose だけである。clone は今もある (盤面・予約・ブロックイベント・時刻を写す)。
- **Rust 版 (RustWorld) は JS 側に写しを持つ**。変化の列で「位置 → BlockState」の表を直す。getBlock と snapshot は、今と同じく同期で答える。
- BlockState は StateId ごとに 1 個だけ作って使い回す。ただし **BE の値を持つ型は別**である (コンパレーターの出力・ホッパーの中身と待ち・ドロッパーの中身・書見台など)。これらは BE の変化と組み合わせて作り直す。
- snapshot は、変化で直した写しを返す。全ブロックを写し直さない。
- 変換は 1 本にする。今は BlockState ↔ vanilla の文字列の変換が 2 本ある (packages/sim/src/mcstate.ts と app/src/nbtIO.ts)。片方だけ直す事故が続いたので、窓口より先に一本化する (M0-5)。
- **fixture の経路は BlockState を通さない**。fixture の文字列をそのままパレットにし、観測も文字列で返す。変換で落ちる情報が無い。
- wasm の読み込みは利用側に置く。@redstone/sim 自身は Vite に依存しない。

**未対応のブロックの扱い**:

| 場面 | 扱い |
|---|---|
| アプリ・埋め込み | initialize が未対応の名前の一覧を返す。同じ盤面から TS で組み直す。画面に印 (「26.3 Rust」か「1.21.1 TS」) を必ず出す |
| EmbedPage の postMessage・SimSession | engine と rulesVersion を引数と戻り値に明示する。呼び出し側が差し戻しを検知できる |
| fixture・テスト・CI | 差し戻さない。fallback は throw で回す |

**描画**:

- viewer に差分の口 (applyChanges) を足す。変わったセクションだけを作り直す。
- 今の作り直しは mixed で 1 回約 26 ms かかる [実測]。これを残すと、Rust にした速さが対話の画面に出ない。
- 予算は「エンジン + 写しの更新 + 描画への反映」の合計で置く (§6)。

## 3. データの持ち方

### 3.1 ブロックの状態と状態表

- 状態は **StateId (u16)** で持つ。エンジンの内部だけの番号で、vanilla の状態 ID とは合わせない (版でずれる。V05 §7.1)。
- ブロックの同一性は **BlockId (名前ごとに 1 つ)** で持つ。これを割らない。次の 4 つが同一性で決まるからである。
  - 予約 tick とブロックイベントの種類の照合 (V02 §7.2・V03 §7.1)
  - 撤去フックを呼ぶ条件 (V04 §7.3)
  - 近隣更新の送り元 (V11 §7 の 3)
  - ドアの「同種は無視」(V11 §7 の 1)
- 番号はビルドの時に決まる。世界ごとに振らない。snapshot・順序の指紋・Worker への受け渡しが、読み込みの順に依存しない。
- 表は 3 段にする。

| 段 | 何を持つ | コミットする物 |
|---|---|---|
| tier 1 | 振る舞いを実装したブロック。全プロパティと値の並び・既定値・Behavior | 自前の書式の表 |
| tier 2 | 振る舞いを持たないブロック (材料と飾り)。名前と、性質を決める規則 (族の規則 + 例外の短い一覧) | 対応するブロックの名前と規則だけ |
| 未知 | 表に無い名前 | 持たない。読み込みを拒み、名前の一覧を返す |

- tier 2 でも、世界に現れるプロパティは全部持つ。オブザーバーと形状更新が、全プロパティの変化を見るからである (V09 §7・V12 §7.1)。
- 性質は状態ごとの密な表へ展開する。展開はビルドの時か、起動の時に 1 回行う。

```rust
#[derive(Clone, Copy, PartialEq, Eq)] pub struct StateId(pub u16);
#[derive(Clone, Copy, PartialEq, Eq)] pub struct BlockId(pub u16);

pub struct StateTable {
    pub block: &'static [BlockId],      // 状態 → ブロック
    pub flags: &'static [u16],          // 導体・信号源・当たり判定がフル・BE あり・硬さ -1・replaceable・solid・アナログ出力
    pub faces: &'static [u32],          // 面の支え (6 方向 × 種類)
    pub push: &'static [PushReaction],  // 26.3 の 5 値のまま
    pub behavior: &'static [Behavior],
}
```

- 性質のビットは別々に持つ。1 つに畳まない (V05 §7.3)。
- 状態の添字は混合基数で計算する。プロパティの書き換えは桁の差し替えで済む。

**生成の手順** (tools/gen-state-table):

1. 入力は 2 つある。V05 §3.7 の手順 A (data report) と手順 B (性質のダンプ) である。どちらも手元で作り、コミットしない。
2. 対応するブロックについて、プロパティの並びと性質の規則を自分で書く (例: スラブは二重のときだけ導体)。
3. 生成器が、全メンバーの全状態について規則とダンプの一致を確かめる。合わなければ、例外の行を足すか族を分ける。
4. 生成物をコミットする。先頭に、生成元の版・コマンド・ダンプのハッシュを書く。今の noteInstrument.generated.ts と同じ扱いである。
5. CI が生成表の範囲を検査する。vanilla の状態 ID を含まないこと、件数が上限の内であること。

**全 1,286 ブロック・35,723 状態の目録は持たない**。「blocks.json などのデータの丸ごとの同梱はしない」に当たりうる。サイズの主因にもなる。対応するブロックの範囲は §11 でユーザが決める。

### 3.2 世界

| もの | 持ち方 | 理由 |
|---|---|---|
| セクション | 16³ の StateId の密な配列 | 参照が配列 1 回で済む (4.1 ns の形 [実測]) |
| セクションの場所 | 世界の広がりを覆う密な格子。外へ広がれば作り直す | ハッシュを引かず、決定的である |
| 近隣の参照 | セクションの中は添字に ±1・±16・±256 を足す。境界をまたぐときだけ格子を引く | 熱い経路を短くする |
| 座標 | i32 の絶対座標。セクションは 16 の倍数にそろえる | ダストの起点の順 (V18 の R1) とピストンの空くセルの順 (V18 の R2) は絶対座標で変わる。予約 tick の入れ物はチャンクごとである |
| 原点 | 取り込んだ回路は元の原点を保つ。エディタの盤面も原点を設定で持つ | locational な回路の結果を変えないため (R16 §4.4) |
| チャンク | 16 × 16 の柱。予約 tick の入れ物・ランダム tick・GameEvent のリスナーの単位 | V01・V02・V10 |
| ランダム tick の対象数 | セクションごとに持ち、書き込みのたびに増減する | V01 §7.2 |
| 範囲外 | void_air として読む (信号 0・非導体) | V05 |
| 「tick 可能か」 | 述語にする。既定は常に真 | V02 §7.3 |

**ハッシュの規則**: ハッシュ集合は所属の判定にだけ使う。反復するのは Vec と挿入順の列だけにする。Rust の標準の HashMap と HashSet は使わない (反復の順が実行ごとに変わる)。clippy の disallowed-types で禁止する。

### 3.3 BlockEntity と ticker

```rust
pub enum BlockEntity {
    Comparator { output: i32 },                    // 0〜15 に丸めない (V07 §7.1)
    MovingPiston { moved: StateId, dir: Dir, extending: bool, is_source: bool,
                   progress: u8, progress_prev: u8, last_ticked: i64 },   // 半分単位 (V13 §7.1)
    Hopper { slots: [ItemStack; 5], cooldown: i32, ticked_at: i64 },
    Container { slots: Box<[ItemStack]> },         // チェストは半分ごと。結合は持たない (V14 §7.1)
    Dispenser { slots: [ItemStack; 9] },
    Crafter { slots: [ItemStack; 9], disabled: u16, triggered: bool, countdown: i8 },
    Lectern { page: i32, pages: i32, has_book: bool },
    Jukebox { disc: u16, elapsed: i64, playing: bool },
    /* … */
}
```

- 位置から引く表は開番地のハッシュ表にする。所属と取り出しだけに使い、反復しない。
- ticker は **全種類を 1 本の列**で回す (V10 §7.2 の 3)。包み (BE への参照 + 生死) を登録順に並べる。
- 除去は印だけ付ける。L13 の走査が届いたときに詰める。
- L13 の最中の追加は pending に入れる。次の L13 の冒頭で末尾へ移す (V01 §7.2)。
- 同じ位置で状態だけ変わったときは順を保つ。別のブロックへ置き換えたら末尾へ移す。ただし新しいブロックが BE を引き継ぐ置き換え (26.3 では銅のチェストと銅のゴーレムの像の酸化・錆止めだけ) は順を保つ (V01 §4.7)。
- 作成と撤去は書き込みの手順の決まった位置で行う。素子は直接いじらない。

### 3.4 予約 tick

V02 §7.1 のとおり 2 層にする。全体のキュー 1 本には畳まない。

```rust
pub struct ScheduledTick<K> { pub kind: K, pub pos: Pos, pub trigger: i64, pub priority: i8, pub sub: i64 }

pub struct ChunkTicks<K> {
    heap: MinHeap<ScheduledTick<K>>,     // (trigger, priority, sub) の順
    present: PosKindSet<K>,              // 入れ物にあるか (所属だけ)
}

pub struct LevelTicks<K> {
    chunks: ChunkGrid<ChunkTicks<K>>,
    next_due: ChunkGrid<i64>,            // チャンクごとの先頭の発火 tick
    run_now: VecDeque<ScheduledTick<K>>, // 今 tick の分
    run_now_set: PosKindSet<K>,          // 今 tick の未実行分 (所属だけ)
}
```

- ブロック用 (K = BlockId) と流体用 (K = FluidId) の 2 式を持つ。予約順のカウンターは Level に 1 つで、2 式が共有する。重複で捨てるときも進める。
- 問い合わせは 2 つに分ける。「入れ物にあるか」と「今 tick の未実行分にあるか」である。合成した関数を作らない (V02 §7.4・V08 §7.2)。
- 集める段は、先頭の発火 tick が今以下のチャンクを併合する。併合の鍵は (優先度, 予約順) である。取り出したチャンクを戻すとき、鍵を取り直す。
- 上限は 65,536 件である。達したら残りを置いたままにし、TICK_CARRYOVER を返す。
- 入れ物の集合から外すのは取り出したときである。未実行の集合から外すのは配送の直前である。
- チャンクの表を回す順 (V18 の R4) は、段 E4 で開番地の写しに替える。それまでは「予約順が一意なので同点が出ない」範囲で使う。読み込んだ予約どうしの同点に達したら、黙って進めず LOADED_ORDER_TIE を返す。

### 3.5 ブロックイベント

- VecDeque と集合の組で持つ。鍵は (位置, BlockId, A, B) である。A と B は i32 のまま持つ (V03 §7.1)。
- 重複を比べる相手は「まだ取り出していない分」だけである。取り出すとき集合から消す。
- 取り出してから処理の関数を呼ぶ。処理中に積まれた分は同じ相で回る。上限は設けない。
- tick をまたいで持ち続ける。snapshot には順序つきで入れる。

### 3.6 近隣更新のスタック

```rust
#[derive(Clone, Copy)]
pub enum Update {
    Simple { pos: Pos, src: BlockId, ori: Option<Orientation> },
    Full   { state: StateId, pos: Pos, src: BlockId, ori: Option<Orientation>, moved: bool },
    Multi  { center: Pos, src: BlockId, skip: Option<Dir>, ori: Option<Orientation>, next: u8 },
    Shape  { dir: Dir, other: StateId, pos: Pos, other_pos: Pos, flags: u16, left: i32 },
}

pub struct Updater {
    stack: Vec<Update>,   // 末尾が上
    added: Vec<Update>,   // 今の 1 件の中で積まれた分 (積んだ順)
    count: u32,           // 最外から受けた件数
    limit: i32,           // 既定 1,000,000。負は無制限
    first_dropped: Option<Pos>,
}
```

- 最外で呼ばれたら、その場で回し切る。相ごとにまとめない (V04 §7.5)。
- Multi は添字を先に進めてから受け手を呼ぶ。続きがある間は stack に残る。
- 入れ子の更新は added に溜める。親の残りより先に走るよう、逆順で stack へ移す。
- count が上限に達したら新しい分だけ捨てる。CHAIN_LIMIT を返し、最初に捨てた座標を 1 回だけ記録する。
- 近隣更新 (NC) は送り元の BlockId を必ず運ぶ。
- Orientation は u8 の番号 1 つで持つ (48 個の表の添字)。段 E5 まで常に「無し」である。項目は Copy の小さな値にし、Vec を使い回す。熱い経路で割り当てない。

### 3.7 乱数と反復順

| もの | 持ち方 | 使う所 |
|---|---|---|
| Level の乱数 | u64 の状態 1 個 + 正規乱数の控え。48 bit の線形合同法。種は引数。snapshot に含める | Level に 1 本 |
| ランダム tick の位置の状態 | i32。wrapping の乗算と加算 | V01 §7.2 |
| 位置で分ける乱数 | ワールドの種と位置から作る | 強い硫黄の周期 (V11 §7 の 8) |
| HashMap・HashSet の写し | 入れ物の配列と、入れ物の中の順つきの列。入れる・消す・拡張・反復を V18 §4.2 のとおりに書く。木構造は実装せず、達したら TREE_BIN を返す | V18 の R1 (ダストの 7 起点)・R2 (ピストンの空くセル)・R8 |
| 開番地の写し | fastutil の規則の写し。キーの型ごとに撹拌を差し替える | V18 の R4・R7・R11 (段 E4) |
| 挿入順の集合 | 挿入順の配列と位置の表。入れ直しで位置を動かさない | V18 の R3・R9・R13 |
| 方向の表 | 定数の配列。宣言順・NC の順・SU の順・水平の順ほか | V04 §7.2・V05 §7.2 |

- 乱数は「引く場所と回数」を合わせる。音だけに使う分も引く (V11 §7 の 8)。
- **V18 の R1 (ダストの 7 起点) は最初から HashSet の写しを通す**。7 要素専用の速い関数は、近道として後から入れる (§4.5)。
- 実機の乱数の列は再現できない。期待値には、列でなく「引く回数」と「結果の集合」を使う (V18 §7.2)。

### 3.8 変化の記録

- 書き込みのたびに、そのマスの印を見る。立っていなければ印を立て、(マス, 書き込み前の状態) を列に足す。
- 書き出すときは、前の状態と今の状態を比べ、違うものだけを出す。そのあと印を消す。
- 何 tick 分たまっても正味の変化になる。列の長さは「書き出しの間に書き換わったマスの数」で頭打ちになる。
- 1 tick の正味の変化は最大で約 900 件である [実測。4 回路]。位置 12 B と状態 2 B で約 13 KB になる。

## 4. tick の進め方と順序の守り方

### 4.1 1 tick と入力

相の順は定数の配列で持ち、単体テストで固定する (V01 §7.1)。

| 順 | 相 | 中身 | 縦切りの時点 |
|---|---|---|---|
| 1 | B2 | 時計を進める | 値だけ |
| 2 | L0 | handling_tick を真にする | 実装 |
| 3 | L2 | 天候 | 空の枠 |
| 4 | L4 | 空の明るさ | 外から与えた値を読む |
| 5 | L5 | game_time を 1 増やす | 実装 |
| 6 | L6 | ブロックの予約 tick。集める → 回す | 実装 |
| 7 | L7 | 流体の予約 tick。L6 が全部終わってから集める | 空の枠 |
| 8 | L9 | ランダム tick | 空の枠 (既定の速度 0) |
| 9 | L10 | ブロックイベントを空になるまで回す | 実装 |
| 10 | L11 | handling_tick を偽にする | 実装 |
| 11 | L12 | エンティティ (在席の検知) | 空の枠 |
| 12 | L13 | pending を移す → ticker を登録順に回す → 除去を詰める | 実装 |

**入力は tick の関数の外で受ける**。呼ばれたその場で、連鎖を最後まで回し切る。

- fixture の規約は「state[t] は tick t の全相の後、tick t の入力の直後」である (tools/mc-harness/README.md の「tick 規約」)。実行器は次の形で回す。
  1. 初めの盤面を置く (§4.2 の「そのまま」)。これは **tick −1 の状態**である。tick 0 の全相は、もう済んだものとして扱う。
  2. t = 0 では **step を呼ばない**。tick 0 の入力だけを入れ、状態を読む。これが state[0] である。
  3. t = 1 〜 ticks では、step を 1 回呼び、tick t の入力を入れ、状態を読む。これが state[t] である。
- step を呼ぶ回数は ticks 回で、ticks + 1 回ではない。t = 0 の前にも step を呼ぶと、初めの盤面に持ち込んだ予約 (fixture の scheduled ほか) が 1 tick 早く発火し、以後の全 tick が 1 つずれる。
  予約も BE も持たない静かな盤面では差が出ないので、テストは step の回数を直に確かめる。
- この数え方は、正解を撮る側と同じである。
  - 26.3 のオラクル (tools/gt-oracle/java/gtoracle/Driver.java の SETTLE → RECORD): settle の最後の tick に tick −1 を撮り、同じ tick の中で tick 0 の入力を入れて tick 0 を撮る。次の tick からは、1 tick 進むたびに t を 1 増やし、入力を入れて撮る。
  - TS の実行器 (packages/sim/src/fixture-driver.ts の runFixtureOnSim): settle した世界から始め、t が 1 以上の時だけ tick を進めてから、入力を入れて読む。
- 今のアプリも、入力の直後に状態を同期で読む。この使い方を保つ。
- 予約の基準の時刻は今の game_time である。入力由来の予約は、tick の中の予約より 1 tick 早く見える (V01 §2.4)。
- 凍結と step は「時計と L4 以外の相を飛ばす。ticker は掃除だけ」で表す。積む側は止めない (V03 §7.3)。

**入力の区間**: 入力には区間の印を付ける。

| 印 | 区間 | 例 |
|---|---|---|
| C | コマンド | setblock |
| A | プレイヤーの操作 | use (右クリック)・place (プレイヤーが置く)・break (プレイヤーが壊す) |
| B1 | 関数 | (今は使わない) |
| B5 | プレイヤーの移動に伴う検知 | プレイヤーの在席 |

- fixture の実行器は、同じ tick の入力を C → A → B1 の順に安定に並べてから適用する。1.21.1 の fixture のうち 2 本が、同じ tick に別の区間の入力を持つ (dust-reshape-stale-target・wire-connect-detector-rail-lectern)。
- アプリの対話の入力は、呼んだ順に適用する。
- fixture の inputs の並びがハーネスの適用順と同じかは、R18 の O2 で確かめる。
- **C と A の前後は [要実機] として残す**。オラクル (c) は入力を全部 1 つの区画で呼ぶので、この前後を確かめられない。V01 §8 のプローブ (RCON の採取系) の結果で決める。
- 在席の入力には「誰が」を持たせる。プレイヤーは B5 (境界)、ほかのエンティティは L12 で検知する。
- **place (プレイヤーが置く)** は、実機の BlockItem の手順に沿う (V04 §4.13)。置き換え可能か → 置く状態 → 支え → 当たり判定 → フラグ 11 の書き込み 1 回 → 読み直し → setPlacedBy の順である。
  /setblock の経路 (V04 §4.11) とは別物で、周りに合わせて直す段を通らない。断る時 (置き換え可能でない・置く状態が「無し」・支えが無い) は、何も書かない。
  - 置く状態は、書き込みの前の盤面で決める (ランプの lit は V11 §4.1。決めてから書く)。置く状態が「無し」になるのは、レバーやトーチの付く面が無い時、ドアの真上が置き換え可能でない時などである。
  - setPlacedBy は、読み直したブロックが置いた物と同じ種類の時だけ呼ぶ (V04 §4.13 の手順 9)。3 素子 (レバー・ダスト・ランプ) と石は持たない。
    BE を持つブロックは、その前に CU を 1 回出す (同じ手順 9)。
  - 当たり判定は、エンティティを持たないエンジンでは常に通る。
  - トーチ (StandingAndWallBlockItem) とドア (DoubleHighBlockItem) は、アイテムのクラスが手順を変える (V04 §4.13 の「BlockItem の子クラスが変える所」)。入れる時に足す。
- **break (プレイヤーが壊す)** は、実機の ServerPlayerGameMode#destroyBlock の手順に沿う (V04 §4.14)。3 素子と石では、回路に効くのは「空気をフラグ 3 で書く 1 回」(Level#removeBlock) で、撤去フックはその書き込みの中で走る。クリエイティブの即破壊とサバイバルで、書き込みは同じである。
  - air を壊しても何も起きない。cave_air は、クリエイティブでは air を書く普通の撤去になる (V04 §4.14 の「空気を壊そうとした時」)。エンジンが air しか持たない間は、今の形でよい。
  - 書くのは流体のブロックである (水を含むブロックなら水)。水を持つ時に足す。
  - 壊す前の処理 (Block#playerWillDestroy) を持つブロック (紐・TNT・ドア・ベッドほか) を入れる時は、V04 §4.14 の表の処理を先に足す。
    書き込みの後の処理 (Block#destroy は動くピストン、Block#playerDestroy は氷と亀の卵) も同じ節にある。
  - 壊す入力はモード (クリエイティブ・サバイバル) を持たない。モードで盤面が違うブロック (TNT・ドア・2 マスの植物・ベッド・ピストンヘッド・氷・亀の卵・ハチの巣。V04 §4.14 の「違い」) を入れる時に、どちらで写すかを決める。
  サバイバルで完了が早すぎた破壊の後追い (L12。V01 §4.10) は持たない。入力は、壊れた時点の 1 回として受ける。
- 壊す入力は、この表の元の版には無かった。redstone-engine が足すと決めた (§2.5 の記録)。

### 4.2 読み込みと settle

ここがずれると、tick 0 の時点で予約順と BE の順がずれる。以後の tick 内の順の比較が全部意味を失う。

| 型 | 手順 | 使い道 |
|---|---|---|
| そのまま (Settled) | 更新なしで置く (strict と同じ)。BE の値は、与えられれば使い、無ければ今の入力から求める。予約は seed だけを積む | fixture。取り込んだ回路の trustAuthored |
| 組み直し (Rebuild) | 更新なしで置く → 全ブロックへ決まった順で NC を配る → 静かになるまで進める (上限つき) | エディタで組んだ回路 |

決め事:

| 項目 | 定義 |
|---|---|
| 置く順 | fixture の blocks の順 (ハーネスが置いた順) |
| BE の ticker の登録順 | 置いた順。保存し直した世界のハッシュの順 (V18 の R7) は段 E4 まで写さない。違いうる点として文書に残す |
| 予約の seed | 列の順に予約の関数を呼んで入れる。オラクル (c) と同じ形である (R18 §4.4)。セーブデータを読むときだけ「−n から振る」(V02 §7.3) |
| Rebuild の NC の順 | オラクルと共有する定義に従う。分かるまでは座標の昇順で仮置きし、O2 で確かめて合わせる |
| settle の名残り | トーチの焼き切れの列・ホッパーの待ち・game_time の位相。今の fixture には無い。O4 で撮れたら seed として入れる |
| 焼き切れの列 | snapshot には入れる。fixture の読み込みでは空で始める (O4 まで) |
| 点検 | fixture を clone し、8 tick 空回しして何も変わらないことを確かめるテストを置く |

**redstone-engine がこの節から外した所** (2026-11-28 の記録。redtact-com/redstone-engine#13)

- 上の表は、エディタで組んだ回路を「組み直し」で読むとしている。redstone-engine は、エディタで組んだ盤面も「そのまま」で読む。組み直しは席だけで、中身を作っていない。
- 理由は 2 つある。
  1. 組み直しは NC を配るだけなので、ダストの形は直らない。ダストの形は形状更新でしか変わらない (V06 §2.1・§4.11)。
  2. 編集の間もエンジンの世界を 1 つ持ち、置く・消すのたびに place・break の入力 (§4.1) を入れる形にした (§6.3 の記録)。
     盤面は、実機と同じ設置の手順でもう直っているので、開始の時に組み直す物が無い。
     - これは前提つきである。編集の世界は step も use もしないので、全部切れのままである (redstone-engine#15)。
       全部切れの盤面は不動点なので、開始の時に新しい世界へ settled で読んでも、置いて組んだ世界と同じになる (#13 の試験。範囲は 1 層・床置きのレバー・全部切れ・点なし・3 素子)。
     - 「そのまま」は予約を引き継がない。編集の世界で積んだ予約は、開始の読み込みで消える。
     - だから、常に信号を出す素子 (トーチなど) や、置いた時に予約を積む素子 (setPlacedBy のダイオードほか。V04 §4.13・V07 §4.13) を入れる時に、
       編集の世界の意味と開始の読み込みの型を、組み直しも含めて決め直す (#15 の「後で」)。
- 取り込んだ回路 (ファイルから読んだ盤面) の扱いは、ここでは決めていない。上の表の「そのまま (trustAuthored)」のままである。

### 4.4 順序の指紋

- trace を有効にした版は、tick ごとに「実行した操作の列」を記録する。
  - NC・SU・CU の実行 (受け手・送り元・種類)
  - 予約 tick の配送 (位置・ブロック・優先度)
  - ブロックイベントの実行
  - BE の tick
- この列から tick ごとのハッシュと件数を作る。fixture ごとの golden として conformance/golden に置く。
- 最適化の PR は、golden が変わらないことを条件にする。golden を変える PR は「挙動の変更」として扱い、典拠のメモの節を書く。
- 件数は揺れない。性能の回帰の目安として CI で見る。
- 指紋は自分の実装の記録である。正しさは保証しない。正しさは実機の fixture (§7) で決める。
- 指紋を取る版 (trace あり) と配る版 (trace なし) は別のビルドになる。CI が、全 fixture で 2 つの版の全状態のハッシュが一致することを確かめる。

### 4.5 入れない最適化・入れる最適化

**入れない** (回数か順が変わる):

| 最適化 | 入れない理由 |
|---|---|
| ダストの最終値を先に求めて一度に書く | 近隣更新の回数と順が変わる (V06 §7.3) |
| ダストが自分へ受ける 6 件の NC を省く | その時点の世界で計算し直すので、結果が変わりうる |
| ダストの接続を覚えておく | 保持値と計算し直した値は一致するとは限らない (V06 §7.2) |
| 予約 tick を全体のキュー 1 本に畳む | 期限切れの順が変わる (V02 §7.1) |
| 更新をためて後で配る・重複をまとめる | 「書き込みが戻った時点で連鎖が終わっている」前提が崩れる (V04 §7.5) |
| 空気への NC を呼ばない | 26.3 は空気にも呼ぶ。費用は表引き 1 回である |
| tick の中の並列化 | 順序が定義できない |
| 回路を論理に直して評価する | tick 内の順とピストンを扱えない (R16 §1.1) |
| opt-level z | tick が 3.9〜4.3 倍遅い [実測] |

**入れる** (読む値と順が同じ):

| 最適化 | 順を変えない理由 |
|---|---|
| 密な配列・整数キー・状態ごとの前計算の表 | 表は純粋関数の前計算である |
| ハッシュ集合を所属の判定にだけ使う | 反復しないので、順に出ない |
| 熱い経路で割り当てない | 処理の中身は同じである |
| 何もしない相を O(1) で抜ける | vanilla もその相で何もしない |
| 観測をコンパイルから外す | 観測は状態を変えない (§4.4 の一致で確かめる) |

**近道の解禁の条件**: 次の 3 つは近道として扱う。段 3 が終わり、26.3 のオラクルとの一致を固定するまで入れない。

| 近道 | 条件 |
|---|---|
| V18 の R1 の 7 要素専用の関数 | HashSet の写しと全数で照合する。原点付近の例外の座標 ((0,1,0)・(1,1,0)・(2,1,0))、負の座標、ハッシュ値が 65536 を超える座標を含める |
| ダストの接続のキャッシュ | 証明できる範囲だけ。測ってから検討する |
| 何も起きない tick の読み飛ばし | 早送りに限る。条件は「期限の来る予約なし・ブロックイベントなし・生きた ticker なし・ランダム tick 0・在席の期間なし・空の明るさと時計を読む素子なし」 |

どの近道も、「あり」と「なし」で全 fixture・差分ファジング・順序の指紋が一致することを条件にする。

### 6.3 起動とメモリの扱い

- 編集画面は wasm を待たずに盤面を描く。待つのは「開始」だけである。準備の前に押されたら待つ。
- 世界を作り直すとき (編集に戻る・リセット) は、世界ごと捨てる。断片化を溜めない。
- ハンドルの解放は dispose で行う。呼ぶ所を決め、FinalizationRegistry を安全網にする。線形メモリは縮まないので、長く動かす e2e でメモリを見る。

**redstone-engine がこの節から外した所** (2026-11-28 の記録。redtact-com/redstone-engine#13。ユーザの 2026-11-28 16:20 までの選択「編集もエンジンで置く」)

- 1 行目の「編集画面は wasm を待たずに盤面を描く。待つのは開始だけ」から外れた。redstone-engine のアプリは、**編集の間もエンジンの世界を 1 つ持つ**。
  置く・消すのたびに Rust の place・break (§4.1) を入れ、返った変化 (§3.8) で盤面を直す。
- 得る物: 編集の 2D に、ダストの本当の形が出る。開始の後の盤面とずれない (全部切れの盤面である間。§4.2 の記録の前提)。ダストの形を決める所が Rust の 1 か所になり、TS では決めない (§8.2 の最後の行の「編集の補助は TS のまま残す」からも外れる)。
- 失う物: 置く・消すは、wasm の読み込み (選んだ時の見積もりは brotli で約 37 KB) を待つ。wasm を取れないと、編集もできない。床は待たずに描く。
- 2 行目・3 行目 (世界ごと捨てる・dispose) は変わらない。

| 11 差分ファジング | 生成した小さな回路の状態とキュー | オラクル (O10) | 手元・夜間 | 落とさない。食い違いを最小化して fixture にする |
| 12 実回路 | 結合テスト | R17 の manifest の回路 | 段 3 | 報告 |
| 13 e2e | アプリの経路 (engine=rust を含む) | — | Playwright | 落とす |

**CI を落とす正解は実機だけ**である。26.3 の fixture と、仕分け済みの A 群 129 本である。TS に寄せる圧力を作らない。

### 7.2 fixture を Rust で読む規則

1. 形式は今のままにする。足すのは R18 §7.2 の任意の欄 (queue・blockEvents・updates・log・startGameTime) と採取系の印だけである。
2. 名前空間を外してキーを並べた文字列で、完全に一致させる。材質は畳まない。
3. 入力の写し方:

| fixture の入力 | Rust での扱い | 区間 |
|---|---|---|
| use | 空の手の右クリックの経路 | A |
| setblock | 26.3 の /setblock の手順 (strict も持つ) | C |
| item | アイテムを置き、変化の通知の CU を出す | C |
| lectern | ページの変更 | A |
| summon・kill | 検知レールの在席 | L12 |
| step | 感圧板の在席 | B5 |
| tp | 何もしない | — |

4. tick の規約は今と同じにする (§4.1)。
5. fixture とテストでは TS へ差し戻さない。

### 7.3 オラクルの欄との比べ方

| 欄 | 比べ方 |
|---|---|
| 予約キュー | 予約順の番号でなく、相対の順で比べる。採取系とエンジンで番号の起点が違う |
| 更新の列 (NC の座標) | 観測の癖をそろえる。オラクルは 6 方向の更新を覗くたびに全方向を報告する (R18 §4.3)。同じ写像を Rust の記録にかけてから比べる |
| ブロックイベントの順・更新の種別 | 採取系が差し替えを使う欄である。差し替えなしの expect と一致することを確かめてから、正として使う |
| 乱数が絡む結果 | 列を期待値にしない。引いた回数と結果の集合で比べる |

### 7.4 オラクル (R18 の O1〜O11) との結び方

| O | 内容 | Rust の側での使い道 | 結ぶ issue |
|---|---|---|---|
| O1・O2 | 起動の土台・入力と settle の写し | 入力の写し方 (§7.2) と Rebuild の NC の順を両側でそろえる | M1-5 |
| O3 | 26.3 の fixture 一式と仕分け | 1.21.1 の合否を置き換える | V-2 |
| O4 | 見えない状態の記録と注入 | 予約キューを tick ごとに比べる。settle の名残りを seed にする | V-3 |
| O5 | tick 内の順の記録 | ブロックイベントの列と NC の座標の列を比べる | V-3 |
| O6 | 案 (a) を 26.3 へ | 採取系どうしの照合。Rust は関わらない | — |
| O7 | 常駐モード | native の CLI と組にして最小化する | V-5 |

**オラクルは M0 と同時に始める**。この設計の値打ち (tick 内の順まで合わせる) は、queue・blockEvents・updates の欄が撮れて初めて確かめられる。欄が撮れる前に、骨格の構造を固め切らない。
素子のマイルストーンに合わせて、その素子のプローブを先に撮る順にする。

### 7.5 TS との差分と台帳

- 同じ回路を TS と Rust に流し、最初に食い違う tick と座標を出す。
- 食い違いは conformance/known-diffs.json に載せる。行は (回路, 最初の tick, 座標の数, 分類, 典拠, 期限) である。

| 分類 | 意味 | 典拠の書き方 |
|---|---|---|
| VP | 版の切り替え点 | V19 §7 の 2 の行 |
| TD | TS の既知の食い違い | 各メモの §9 の行、R16 の R-n の番号 |
| RG | Rust の未実装 | マイルストーンの issue |
| UN | 未分類 | 調べる issue が必須 |

- **差分は合否にしない**。CI は差分の表を報告するだけである。TS は 1.21.1、Rust は 26.3 なので、差があるのが正しい場合がある。
- CI が落とすのは台帳の書式だけである (分類と典拠があること。UN に issue があること)。
- UN は 26.3 の実機で決着させる。TS に合わせて Rust を直すことはしない。
- main の既定を切り替える基準に「UN が 0」を入れる (§8.3)。

### 7.6 [要実機] の台帳

- docs/vanilla の [要実機] 211 件を conformance/pending-probes.json に 1 件 1 行で持つ。項目は (メモの節, 内容, 仮の実装, プローブ名, 答えの fixture) である。
- 仮の実装は「読解で最もありそうな側」に倒す。コードの該当箇所に `UNVERIFIED(V06-§5.2)` の形の印を付ける。
- CI が印と台帳の対応を確かめる (片方だけに無いか)。
- プローブで答えが出たら、fixture 名を書いて印を消す。メモの [要実機] も同じ PR で直す。

### 7.7 rstest と trace

- rstest の文法と構文解析は TS の 1 本のままにする。実行器にエンジンの選択を足す。
- rstest の meta に source (oracle か ts) を足す。今の 131 本は ts (期待値は TS が出した値の写し) である。Rust の合否に使わない。
- trace の断言と 4 本の .trace も TS の写しである。Rust の合否に使わない。
- インラインの回路は fixture の定義に起こし、O11 で撮る。撮れば両方のエンジンの正解になる。
- Rust は構造化した事象だけを出す。08 記法への整形は、今の TS の整形の 1 本にまとめる。SU と CU の行を足す。

### 7.8 CI

| ジョブ | 契機 | 中身 | 落とす条件 |
|---|---|---|---|
| rust (新設) | PR・push | toolchain の固定とキャッシュ・fmt・clippy・cargo test・wasm のビルドと wasm-opt・サイズの報告 | どれかの失敗・サイズの上限超え |
| test (既存) | PR・push | rust の wasm を成果物で受け取る。vitest (TS の回帰・衛生 + Rust の適合・指紋・台帳の書式) | 今の条件 + Rust の合否 |
| e2e (既存) | PR・push | 今のスモーク + engine=rust のスモーク | 今のとおり |
| deploy・pr-preview (既存) | push・PR | wasm を作ってからアプリを組む (wasm を必須にする) | ビルドの失敗 |
| oracle (新設。O8) | 週次・手動 | 26.3 で撮り直し、変わった fixture を PR にする。状態表の鮮度も見る | jar を残さない。fork では動かさない |

- オラクルは PR の CI では回さない (jar を取るため)。fixture はコミット済みの期待値で比べる。
- wasm が無くても、TS だけのビルドとテストは通る。Rust の分は skip する。

## 9. 著作権の運用

### 9.1 メモから書く手順

| 役 | 読んでよいもの | 書くもの |
|---|---|---|
| 読む役 (メモの担当) | 26.3 のデコンパイル | docs/vanilla (自分の言葉・数値・クラス名#メソッド名) |
| 書く役 (Rust の担当) | docs/vanilla・fixture・オラクルの出力・本書 | Rust |

1. 実装の issue に、典拠のメモの節と、通す fixture を書く。
2. 書く役は、メモ・fixture・本書だけを見て Rust を書く。
3. メモで足りなければ、実装を止めて「メモへの質問」の issue を立てる。読む役がメモを直す。書く役は直ったメモから書く。
4. メモの PR (docs だけ) と実装の PR を分ける。Rust の挙動は、すべて日本語のメモまで辿れる。
5. **同じセッションが両方の役をしない**。Java を見ながら Rust を書く経路を作らない。

### 9.2 Java を見ながら書かない工夫

| 工夫 | 中身 |
|---|---|
| 読み取りの拒否 (必須) | 書く役のセッションは、デコンパイルの出力 (tools/decompile/out) と、Nucleation・redsim の clone を読めない設定にする。設定はユーザが入れる (§11 の 4) |
| 作業場所 | 実装用の worktree にはデコンパイルの出力を作らない。追跡していないので、何もしなければ存在しない |
| 構造を写さない | モジュールはメモの分け方に合わせる。振る舞いは列挙と表で振り分ける。Java のクラスの階層を trait の階層で写さない |
| 関数の切り方 | Rust の都合で決める。メモの表の単位 (例: V07 §7.2) を採る所は、その旨とメモの節を PR に書く |
| 名前 | メモの用語 (NC・SU・CU・相の番号・R 番号) とプロパティ名を使う。非 snake_case の名前を deny にする |
| コメントの典拠 | 「docs/vanilla の節」と、要るなら「26.3 クラス名.メソッド名」の名前だけ。区切りは docs/ip-policy.md の例と今の TS のコメントに合わせて「.」にする (メモの中の「#」はメモ集全体の表記)。Java の文・式・シグネチャは書かない |
| ほかのエンジン | Nucleation (mc-tick) と redsim は、依存にしない・読まない・写さない (R16 §5)。借りるのは挙動の事実とテストの手法だけである |

「実行時のデータと順序を同じにする」設計は、関数の構成まで vanilla に寄りやすい。R16 §5 が Nucleation に指摘した「機械的な翻訳に見える」状態に近づく危険がある。レビューで見続ける。

### 9.3 CI の見張り

| 見張り | 中身 |
|---|---|
| 逐語引用 | tools/ip-hygiene.test.ts の対象に .rs と .toml を足す。コメント行に今の Java の字面の規則を当てる |
| 絶対パス | 今の検査が .rs も見る |
| 依存 | Cargo.lock の名前を許可リストと照合する。rse-java・rse-core・rse-wasm は外部の依存なし。Nucleation・mc-tick・redsim は禁止 |
| データの持ち込み | include_bytes と include_str は、決めたフォルダの下だけ |
| Mojang 由来のファイル | jar・class・blocks.json・reports・mappings・レシピ・ルートテーブル・タグの追跡を禁じる |
| 生成表の範囲 | vanilla の状態 ID を含まない。件数の上限を置く |
| 大きさ | tools/repo-size.test.ts の対象に crates/ と conformance/ を入れる |
| 反復順 | clippy で標準の HashMap と HashSet を禁じる |
| unsafe | rse-java と rse-core は forbid。unsafe は rse-wasm だけ |
| PR の確認欄 | crates/ を触る PR に付ける (下の 5 項目) |

PR の確認欄:

- 典拠はメモの節で書いた
- 作業中にデコンパイル・Nucleation・redsim を開いていない
- Java のメソッドを 1 対 1 で写していない
- 仮置きには UNVERIFIED の印と台帳の行がある
- fixture の expect を Rust に合わせて書き換えていない

### 9.4 データの扱い

- 状態表は「派生した事実の表」としてコミットする。書式・番号・並びは自前で、対応するブロックだけを持つ (§3.1)。
- 生のファイル (data report・性質のダンプ) は手元で作り、コミットしない。
- クラフターのレシピ・ルートテーブル・タグは同梱しない。口だけ決め、未対応は「無し」として扱う (V12 §7.5)。
- 円盤の長さ・音色・アイテムの上限など、既に自前で測って持っている表は今の作り方 (実機から書き出す) を続ける。
- 生成の鮮度は、jar を取る週次の仕事の中で確かめる。公開の PR の CI では jar を取らない。

## 12. 比べた案と採点の要約

### 12.1 3 つの案

| 案 | 方針 | 強み | 弱み |
|---|---|---|---|
| A 忠実性優先 | 26.3 の実行モデルを Rust のデータ構造へそのまま持つ。近道は 1 つも使わない | 順序の仕組みを最も落とさない。Orientation の席・入力の区間・読み込み直しの順・音だけの乱数まで置き場がある。[要実機] の台帳と近道の条件を持つ | 基盤が重く、素子が動くまでが長い。全ブロックの目録が同梱の決まりとサイズに当たる。入力の位相の書き方が fixture の規約と食い違う。読み込みと settle の定義が無い。新しいパッケージが下流を壊す。速さとサイズは未測定 |
| B 性能とサイズ優先 | データ指向。密な配列・前計算の表・整数キー。サイズの予算を CI で守る | 速さとサイズの裏づけが最も厚い。追加の実測 (同じ作りの JS は 2.2 倍・描画が律速) がある。入れない最適化の表と順序の指紋を持つ | 「見た目つきの種類」がブロックの同一性を割る。世界ごとの番号が snapshot を読み込み順に依存させる。写しが BE の値を落とす。V18 の R1 を写しと照合しない。trace なしの別ビルド。[要実機] の台帳が無い。ダストを Opus に割り当てた |
| C 統合と移行優先 | 入れ方を先に決める。窓口・切り替え・差し戻し・検証の資産の再利用 | 今のリポジトリと下流に最も合う。読み込みの 2 つの型・オラクルとの比べ方・rstest の出どころの区別・切り替えの基準を持つ | 内部は「一例」で、近道を禁じる規則も指紋も無い。サイズの予算が緩い。描画の律速を扱わない。入力を呼んだ順にする。差分で CI を落とすと TS に寄る圧力がかかる。状態表の範囲を保留している |

### 12.2 点数

| 採点 | 観点 | A | B | C | 勝ち案 |
|---|---|---:|---:|---:|---|

| 2 | 工学 | 41 | 52 | 53 | C |

- 採点 1 は、合計では C が上だが A を選んだ。ユーザの目標が「全く同じ挙動」なので、正確さを決める規則 (近道の禁止・写しの照合・読み込み直しの順) を持つ案を重く見た。枠は C に載せられると判断した。
- 採点 2 は C を選んだ。1 人 + AI で長く続く作業の主な危険は、途中で利用者と下流を壊すことと、実機との食い違いが黙って溜まることである。内部は B の持ち方に差し替え、A から役の分離と V18 の R1 の写しを取り込むよう求めた。
- 2 つの採点は勝ち案で割れた。しかし求める合成は同じである。**順序の規則は A、持ち方は B、枠は C** にする。本書はこの合成で書いた。

| 読み取りの拒否が提案どまり (C) | 必須にした。設定はユーザが入れる (§9.2・§11 の 4) |

### 12.4 残る危険

| 危険 | 抑え方 |
|---|---|
| オラクルが遅れ、tick 内の順を確かめられない期間が延びる | M0 と同時に始める。素子ごとにプローブを先に撮る |
| [要実機] の答えが、骨格の層で仮の実装を外す | 構造を vanilla と同じ単位にしてある。直す場所は 1 か所だが、fixture の撮り直しが連鎖しうる |
| 速さかサイズが予算に届かない | 縦切りで早く測る。近道は条件つきで後から入れる |
| 役を分けると、メモの不足のたびに往復が出る | メモの粒度が足りるかは M1-3 で分かる。足りなければ進め方を見直す |
| 移行の間、エンジンが 2 本になる | TS の新しい挙動を P1 で止める |
| 乱数が絡む結果は実機と同じ列にならない | 結果の集合で示す。利用者への見せ方は UI の課題として残す |
| 席だけ空けた部分が長く未検証で残る | 席の形のテストを縦切りから置く |
| 26.3 への切り替えで、利用者と下流に見える挙動が変わる | 版の印・リリースノート・下流の probe の結果を先に渡す |
| 計測は Node の V8 だけである | 3 ブラウザの計測を M0-6 で足す |
